# M9c: K 分割がプリフェッチに負ける理由 → **`async_eval` が呼び出し側を止める**。直接読み + K4 バッチ + bf16 norm で **9.01 → 7.90 s/step**

- 測定日: 2026-09-22
- 機材: Mac mini (Apple M6) 16GB、macOS 27.0、MLX 0.32.0、GPU 独占
- 実装: 測定は `05a23e2` の上(`src/` 未変更)。§5 の本番は M9c の実装後(`krea2_weight_stream.py` / `feed_forward.py` / `common.py` / `krea2_staged_loader.py`)
- 再現: `tools/bench/stream_ab.py --model ~/Library/Caches/mflux/16gb-bench/krea2-lowram --config ...`
  (本番と同じ 28 実ブロックのストリーミングループ。ウォームアップ 1 ステップ + 計測 2 ステップ、
  `compute` はブロックの計算の壁時間、`prefetch` は裏で読んだ時間、`bind` は表で読んだ時間、
  `drop` は計算後の後片付け(スレッド版では join 待ちを含む))
- 計画: [DiT を天井に近づける](../../.cursor/plans/2026-09-22-krea2-dit-ceiling.md) §M9c
- 前提: [M9b](2026-09-22-m9b-block-budget.md)(隙間の正体は独立カーネルの並行ディスパッチ)

## 0. 結論

M8c の「K 分割は単体 −30 ms、本番 +42 ms」の正体は**キャッシュでも帯域でもなく、MLX の
`async_eval` が GPU の仕事を約 50 ms 分しか先に進めず、残りは主スレッドが次に MLX を呼ぶまで
待つ**こと。本番では主スレッドが 461 MB の読み(`mx.eval` の Load)で 115〜140 ms 離れる。
その読みの eval 自身が途中で GPU を押すので、ops の少ない K1 は +3〜20 ms で済み、
ops の多い K4 は +50〜70 ms 食らう。

| 主スレッドが `async_eval` の後にすること | K4 の compute(単独 300 ms) |
|---|---|
| すぐ `eval(out)`(読みなし) | 296〜305 |
| 50 ms 眠る | 299(無害) |
| **100 ms 眠る** | **347(+47)** |
| **250 ms 眠る** | **497(+196 ≈ 250 − 54)** |
| 150 ms GIL を握って spin | 386 |
| 純 memcpy 461 MB(22〜38 ms) | 302〜313 |
| MLX のコピー 461 MB(19〜20 ms) | 306〜316 |
| **本番の読み(`mx.load` + eval、115〜138 ms)** | **365〜373** |
| 読みを 150 ms 遅らせてから | 522〜526 |

→ **GPU が独走できるのは約 50 ms。** それ以上主スレッドが離れると、離れた時間がそのまま
計算時間に乗る(sleep 250 → +196)。

## 2. 直接読み(`direct`): スレッドは preadv だけ、主スレッドは `eval(out)` に張り付く

MLX のバッファは numpy の buffer protocol で**書ける**(`np.frombuffer(arr)` は writeable、
`os.preadv` で直接読める。bf16 は uint16 で確保して `view(bf16)`、バッファは共有される)。
次ブロックの配列を先に確保し(`mx.zeros`、GPU の fill 約 7 ms)、スレッドが safetensors の
オフセットから `preadv` でバッファに直接読む。スレッドは MLX を一切呼ばず、主スレッドは
`mx.eval(out)` で GPU を押し続ける。

| 構成 | compute | 裏の読み | bind(確保) | drop(join) | 1 ステップ |
|---|---|---|---|---|---|
| direct:1 | 333〜338 | 125 | 6.7 | 0.2 | 9.52〜9.65 |
| direct:4c | 306〜311 | 132〜135 | 17 | **66〜70** | 11.0 |
| direct:4c:pread:nocache | 307 | 149 | 18 | 84 | 11.4 |

- **GPU は止まらない**(K4c で 306〜311、読みなしの 300 と同じ)。
- しかし K4c では join 待ち 66〜70 ms が残る: 読みは 134 ms なのに compute(306)の終わりに
  間に合わない。**スレッドの開始が遅れている**疑い(K1 では待ち 0.2)。計器を付けて §3 で確認。
- K1 の direct は compute +11(スレッドの preadv が GPU と帯域を分け合う分と、確保 6.7 ms)で、
  本番の main:1 より遅い。**direct は K4 と組み合わせないと意味がない。**

## 3. join 待ちの正体 → **`mx.async_eval` 自身が 100〜244 ms ブロックする**

`direct` に計器を付けた(`async_ms` = `mx.async_eval(out)` の所要時間、`tlag_ms` = スレッド起動の遅れ、
`tend_ms` = スレッドの読み終わり − compute の終わり):

| 構成 | compute | 裏の読み | drop(join) | **async_eval** | tlag | tend |
|---|---|---|---|---|---|---|
| direct:1 | 338.8 | 125.2 | 0.2 | **101.0** | 0.1 | −112 |
| direct:1d | 340.0 | 124.5 | 0.2 | 124.1 | 0.1 | −91 |
| direct:4c | 303.7 | 126.5 | **62.4** | **229.1** | 0.1 | +62 |
| direct:4cd | 300.0 | 124.3 | 79.2 | **244.0** | 0.1 | +79 |

- **`mx.async_eval` は非同期ではない。** K1 で 101 ms、K4c で 229〜244 ms(compute の 8 割)
  呼び出し側を止める。MLX は未完了のコマンドバッファ数に上限を持ち、encode 中に上限に当たると
  呼び出しスレッドを待たせる(ops の多い K4 ほど長い)。`MLX_MAX_OPS_PER_BUFFER=1000` でも
  main:1 335 / main:4c 364 / sleep100 346 で**変わらない**。
- これで §0 の全部が説明できる: 「GPU が独走できる約 50 ms」は async_eval が返った時点で
  コミット済みだった分。主スレッドが sleep / spin / 読みで離れると、残りは次の MLX 呼び出しまで
  進まない。本番(main:1)は読みの `mx.eval` が MLX 呼び出しなので押せるが、K4 は async_eval が
  返るまでに読みの開始が遅れ、しかも ops が多くて押し切れない。
- `direct` の join 待ちも同じ: スレッドを async_eval の**後**に起動していたので、K4c では
  244 ms 経ってから 126 ms の読みが始まり、compute の終わりに 62〜79 ms 間に合わなかった。
  **スレッドは async_eval の前に起動する**(スレッドは MLX を呼ばないので安全)。§4 で測る。

## 3b. 実データ依存でブロック内の matmul を直列化する → **ブロックでは効かない**

| 構成(単体、block_budget `--only seq`) | ms |
|---|---|
| block | 317.1 |
| block, 1d(attention の 4 射影と gate/up を `x + 0*prev[..., :1]` でつなぐ) | 320.2(+3.1、リンク 4 本の値段) |
| block, 4c | 276.9 |
| block, 4cd(4 片もつなぐ) | 279.9(+3.0) |
| block, 4cd, norm bf16 weight | 270.5 |
| 本番形 main:1d / main:4cd | 347.6 / 389.0(main:1 336.0 / main:4c 364 より遅い) |

- M9b §3c の単体ペア(`[gate(o), up(o)]` 127 → データ依存で 98)で見えた並行ペナルティは、
  **ブロックの中では起きていない。** ブロック 317 ≈ matmul 単体の和 256 + sdpa 27 + 要素演算 34 で、
  和より遅い分がない。M8 の「鎖が単体和より 40 ms 遅い」は、中間出力を全部返す合成鎖の
  artefact だった(M9b §2 の隙間はその鎖の中だけの現象)。
- **ブロックの残り予算は `mlp.down` の崖(47 ms)と要素演算(34 ms)だけ。** 直列化は不採用。

## 4. ping-pong 直接読み(スレッドを async_eval の前に起動、バッファは 2 組を交互に使い回す)

`mx.zeros` の fill も precut もやめ、ブロック形の配列を 2 組だけ確保して、i+1 を i−1 が使った組に
preadv で読む。スレッドは `mx.async_eval(out)` の**前**に起動する。

| 構成 | compute | 裏の読み | bind | drop(join) | 1 ステップ | async_eval |
|---|---|---|---|---|---|---|
| main:1(本番) | 323.9 | 118.0 | 0 | 0.2 | **9.07** | |
| pingpong:1 | 342.3 | 126.2 | 0 | 0.2 | 9.59 | 105 |
| **pingpong:4** | **321.4** | 125.9 | 0 | **0.2** | **9.00** | 256 |
| pingpong:4c | 321.4 | 126.1 | 0 | 0.2 | 9.00 | 256 |
| direct:4c(スレッド先行) | 322.2 | 134.1 | 14.6 | 1.3 | 9.47 | 247 |
| none:4(読みなしの K4) | 289.3 | — | 117.2 | 0.1 | 11.38 | |
| pingpong:4(2 回目) | **311.4** | 126.2 | 0 | 0.2 | **8.72** | 247 |
| main:1(2 回目) | 337.4 | 118.0 | 0 | 0.2 | 9.45 | |

- **join 待ちは消えた**(0.2 ms)。読みは完全に裏に隠れる。
- しかし K4 の素の速さ(289)には届かない: **裏で 461 MB を読むこと自体が compute に +22〜32 ms**
  乗る(pingpong:4 311〜321 vs none:4 289)。純 memcpy の stand-in では +5〜10 だったので、
  SSD の DMA と CPU の読みが GPU と何かを分け合っている。`F_NOCACHE`(ページキャッシュ経由の
  コピーをなくす)でも compute は変わらなかった(§2)ので、コピー回数ではない。
- 精算: main:1 に対して pingpong:4 は **−12〜−26 ms/ブロック = −0.3〜−0.7 s/step(4〜8%)**。
  同一セッション内で main:1 自体が 324 → 337 と動く(温度かページキャッシュ)ので、
  隣り合わせて交互に測った差で見る。precut(4c)は要らない(4 と同じ)。
- pingpong:1 は main:1 より遅い(+18)。**直接読みは K 分割と組み合わせてだけ意味がある。**

## 4b. `mlp.down` の K4 を 1 本のバッチ qmm にする(`--only ksplit`)

| 形 | ms |
|---|---|
| down 1 本(K=16384) | 92.4 |
| 4 片のループ + 加算 3 本 | 53.1 |
| **(4, M, 4096) @ (4, N, 1024) のバッチ qmm 1 本 + sum** | **50.8** |
| block / block 4c / **block 4b** / **block 4bn** / block 1n | 317.9 / 277.8 / **275.4** / **265.7** / 308.9 |
| 本番形 main:1 / **pingpong:4bn**(交互 2 回) | 328.4, 339.3 / **307.5, 303.9**(1 ステップ 9.20, 9.51 / **8.62, 8.51**) |

ops が減る(qmm 4 + add 3 + slice 4 → qmm 1 + sum 1)ので `async_eval` の待ちも 256 → 103 ms に縮む。
重みの面への並べ替え `(N, K/4) → (4, N, K/4/4)` は bind ごとに 1 回(コピー約 3 ms、compute に含む)。
分割和との max |diff| は 64(値 8192〜16384 の領域で bf16 1 ULP)。

## 5. 本番(実装後、swapwatch 越し、4 ステップ)

採用した構成: **(1) 2 組のブロック形バッファに、`async_eval` の前に起動したスレッドが `preadv` で
直接読む**(`Krea2BlockStream.start_read` / `finish_read`)、**(2) `mlp.down` を K4 のバッチ qmm**
(`Krea2SwiGLU.down_splits = 4`)、**(3) RMSNorm の float32 往復をやめる**(`Krea2RMSNorm.native_dtype`)。
(2)(3) は `--block-streaming` の経路だけが有効にする(`Krea2StagedLoader.DOWN_SPLITS / NATIVE_NORM`)。
常駐モードの挙動は変えていない(`attach` の既定はオフ、既存テストはビット一致のまま)。

### 5b. M3 Pro の verdict について

M3 Pro は作業機で、測定中も別のセッション(エディタ、ブラウザ、この作業のエージェント)が
動いていた。swap used は測定前から 215 MB あり、swapouts は機械全体で 8 ページ(swap used の
増分 0.1 MB)。HANDOFF §6 の「数十ページ規模は外来と区別できない」の範囲だが、**規約どおり
clean ではないので M3 Pro の回帰は採用値にしない**。速度(22.89 vs 22.96)と footprint(5.04)は
記録として置き、常駐アプリを落として(または再起動して)`iogpu.wired_limit_mb=0` の宿題と一緒に測り直す。

## 6. 踏んだもの

- **`mx.async_eval` は 100〜250 ms 呼び出し側を止める。** 「裏で何かする」設計は、その何かを
  async_eval の前にスレッドで起動しておくこと。主スレッドは `mx.eval(out)` に張り付かせる。
- **MLX のバッファは numpy 経由で書ける**(`np.frombuffer(arr)` を writeable にして `os.preadv`)。
  bf16 は uint16 で確保して `.view(mx.bfloat16)`(バッファ共有)。`mx.zeros` は密な実バッファ。
- **K 分割の面のキャッシュを bind ごとに解放する。** 解放しないと 28 ブロック分(約 3 GB)が残る
  (`stream_ab.py` の peak memory が 7.8 GB だったのはこれ)。`Krea2SwiGLU.release_down_planes()`。
- `mx.depends` は GPU の直列化にならない。`mx.compile` は `fast.rms_norm` を含むと遅くなる。
- ページキャッシュの状態で読みは 86〜139 ms 動くので、A/B は同一セッションで交互に測る。
