# M9: この GPU の天井と、MLX が届いていない場所 → **崖は MLX のカーネル、天井は 19 TFLOPS**

- 測定日: 2026-09-22(M6 mac mini の発売日)
- 機材: Mac mini (Apple M6) 16GB、macOS 27.0 (26A428)、GPU 12 コア(`applegpu_g18g`)、MLX 0.32.0(比較で 0.32.2)、PyTorch 2.14.0(MPS)
- 再現: `tools/bench/ceiling_probe.py`(MLX 側)、`tools/bench/mps_probe.py`(PyTorch MPS 側。torch は
  `uv run --no-project --isolated --with torch --python 3.12` で使い捨て環境に入れる)
- 計画: [DiT を天井まで持っていく](../../.cursor/plans/2026-09-22-krea2-dit-ceiling.md)
- GPU は独占(別の python プロセスなし、load 1.7)。合成テンソル、ウォームアップ 3、8 回平均

M8 で 21.2 → 9.26 s/step になったが、**発売日の M6 でこれは遅すぎるのではないか**、という疑問に
数字で答える。問いは 2 つ: (1) このシリコンは行列積を何 TFLOPS まで出せるのか、
(2) その天井に対して本番の 1 ステップはどこで負けているのか。

## 0. 結論

| | |
|---|---|
| シリコンの天井(密 fp16/bf16 行列積) | **約 19 TFLOPS**。MLX(4096³)19.2、PyTorch MPS(4096³〜8192³)18.7〜19.0 で一致 |
| MLX の q8 行列積、Krea 2 の 7 つの形 | 16.9〜17.6 TFLOPS(天井の 90%) |
| **MLX の q8 行列積、`mlp.down` 16384→6144** | **9.1 TFLOPS(天井の 48%)**。同じ形を MPS は **17.9**。0.32.2 でも 8.7 |
| MLX の密 bf16 も K ≥ 8192 で落ちる | 8192³ 12.0(MPS 19.0)、16384→6144 9.2(MPS 18.0)。**崖は qmm 固有ではなく MLX の GEMM 全般** |
| attention(sdpa、48/12 ヘッド、4126 トークン) | MLX 17.3、MPS 17.2。**同等** |
| 1 ステップの理論下限(1024²、112 TFLOP を 19 TFLOPS で) | **約 6.0 s**(+ ブロック外 0.2 s) |
| いま | 9.26 s。**下限の 1.5 倍** |

**「おかしい」のは 9.26 s のうち 1.3 s で、正体は `mlp.down` の MLX カーネルが MPS の半分の速さで
走っていること。** 残りの差は、未融合の要素演算(0.5〜0.7 s)と、MLX の q8 カーネルが天井より
1 割遅い分(0.5 s)。シリコン側に隠れた性能はない: MPS(Apple 自身の Metal カーネル、neural
accelerator 込み)でも 19 TFLOPS で頭打ちなので、**19 TFLOPS が M6(12 コア)の実力**。

## 1. 密行列積の天井(MLX vs MPS)

| 形 | MLX bf16 | MLX fp16 | **MPS fp16 / bf16** |
|---|---|---|---|
| 2048³ | 8.03 | 13.07 | — |
| 4096³ | **19.19** | 19.10 | 18.72 / 18.73 |
| 6144³ | 17.23 | 17.64 | 18.77 / 18.81 |
| 8192³ | **12.02** | 11.96 | **18.98 / 18.99** |
| 4126×6144 → 16384 | 10.35 | — | 17.88 / 17.90(46.4 ms) |
| 4126×16384 → 6144 | **9.15** | — | **17.89 / 17.97(46.3 ms)** |

(TFLOPS。MLX の密 bf16 の 2 行は q8 を `mx.dequantize` した重みで測った)

- **MPS はどの形でも 18〜19 で平ら。MLX は 4096³ でだけ 19 に届き、K が大きくなると崩れる。**
- 密 bf16 の 6144→16384 が 10.35 なのは意外だが本番には無関係(本番は q8 で 17.0)。

## 2. q8 の崖は K で決まる

`N=6144, M=4126`、K を振る(MLX 0.32.0 / 0.32.2):

| K | 0.32.0 | 0.32.2 |
|---|---|---|
| 2048 | 17.44 | — |
| 4096 | 17.59 | — |
| 6144 | 16.92 | 16.96 |
| 8192 | 16.44 | 16.05 |
| 12288 | 12.38 | 11.81 |
| **16384** | **9.09(91.4 ms)** | **8.74(95.0 ms)** |

- 8192 から緩やかに落ち始め 16384 で半分。**離散的なカーネル切り替えではなく、キャッシュ容量の
  形**(K パネルがオンチップに収まらなくなる)。M8c で K を 4 分割すると戻った(15.7)のと整合する。
- **0.32.2 は直していない**(release notes の `qmm_t_nax` の変更は M が 1 ブロックに収まる場合のみ)。
- group size を 32 / 64 / 128 にしても 8.8 / 9.1 / 9.9、fp16 の活性でも同じ、M を 2048 / 8192 に
  しても 9.0 / 9.0。**形以外の何を変えても動かない。**
- **ビット数は効く**(§4): 同じ形で q6 11.9、q4 14.4。重みのバイト数に比例して速くなるので、
  崖の中では**メモリ帯域律速**になっている。

## 3. attention は MLX と MPS で同等

| | ms | TFLOPS |
|---|---|---|
| MLX sdpa GQA(48/12、L=4126、D=128、bf16) | 24.2 | 17.3 |
| MPS sdpa GQA、同形 | 24.4 | 17.2 |
| MPS sdpa、k/v を 48 に repeat | 24.8 | 16.8 |

attention に伸びしろはない。天井そのもの。

## 4. ビットを減らすと計算は速くなるか(q8 を疑うための測定)

Krea 2 の 3 つの形、bf16 活性、MLX 0.32.0:

| 形 | q8 gs64 | q6 gs64 | q4 gs64 | q4 gs32 | mxfp8 gs32 |
|---|---|---|---|---|---|
| 6144 → 6144 | 16.89 | 17.01 | 18.11(**+7%**) | 17.91 | 16.96 |
| 6144 → 16384 | 17.00 | 17.12 | 18.21(**+7%**) | 18.03 | 17.11 |
| **16384 → 6144(崖)** | 8.97 | 11.94 | **14.36(+60%)** | 13.80 | 10.00 |
| 1 ブロックの重み | 461 MB | 約 350 | 約 245 | 約 270 | 約 450 |

- **崖の外では q4 は q8 の 7% 速いだけ。** neural accelerator は計算律速で、ビット数はほぼ関係ない。
- **崖の中だけ q4 が 60% 速い。** これは崖が帯域律速だからで、崖を K 分割で消せば(15.7 TFLOPS)
  q4 の優位は 7% に戻る。
- mxfp8(8 ビットの別方式)は崖で 10.0。動かす価値なし。
- 1 ステップに換算: **q4 で全層を置き換えても −1.3 s/step(9.26 → 約 8.0)で、これは `mlp.down` の
  崖を直すのと同じ額。崖を直したあとに残る q4 の取り分は 7% ≈ 0.5 s/step。**
  I/O は既に計算の裏に隠れているので(M8b)、ブロックが 461 → 245 MB になっても
  ステップ時間は変わらない(プリフェッチの汚染が減る分、1280² で最大 0.9 s。§5)。
- **判定: q8 のまま。** RAM の制約が消えたのは事実だが、計算効率で見ても q4 は 7% で、
  描き込みが減る代償(README §方針)に釣り合わない。

## 5. 本番 1 ブロック(1024²、323 ms)の予算

M8 の内訳に今日の数字を当てる:

| | ms | 天井なら | 差 |
|---|---|---|---|
| 7 つの速い matmul(wq/gate/wo ×3、wk/wv ×2、gate/up ×2) | 163 | 150(19 TFLOPS) | 13 |
| **`mlp.down` 16384→6144** | **93** | **46**(MPS の 17.9) | **47** |
| sdpa | 27 | 25 | 2 |
| 要素演算(norm ×2、変調、残差、silu×up、RoPE、QK norm。M8 §3) | 約 30 | 融合すれば 10〜15 | 15〜20 |
| 本番の上乗せ(`update`、Python、プリフェッチの汚染) | 3〜5 | 3 | |
| **合計** | **323** | **≈ 235** | **≈ 90** |

1 ステップ = 28 × ブロック + 0.22 s(txtfusion / first / last / サンプラ)。

| 段 | ブロック | 1 ステップ |
|---|---|---|
| いま | 323 ms | **9.26 s** |
| `mlp.down` の崖を消す(−40〜47) | 約 280 | **約 8.0 s** |
| + 要素演算の融合(−15〜25) | 約 260 | **約 7.5 s** |
| 天井(全 matmul 19 TFLOPS + sdpa 17) | 213 | **約 6.2 s** |

**現実的な到達点は 7.5 s/step 前後(いまの 1.25 倍)。それ以上は MLX のカーネルが MPS に
追いつくかどうかで、fork の外の話。**

プリフェッチの汚染は 1024² で +3〜5 ms/ブロックだが、**1280² では +32 ms(0.9 s/step)**
(M8b §2)。K 分割が本番で負けた +42 ms(M8c)も同じ現象と考えるのが自然:
崖のカーネルはキャッシュに敏感で、裏で 461 MB を memcpy する読み込みがそれを追い出す。

## 6. ComfyUI(PyTorch MPS)に移れば速いか

行列積の天井は MPS のほうが素直(K の崖がない)だが、**このマシンで速くはならない**:

| | MLX(いま) | MPS で同じことをすると |
|---|---|---|
| 7 つの速い matmul | q8 カーネル 17.0 TFLOPS、逆量子化なし | 密 17.9 TFLOPS + **逆量子化 11 ms / 100 MB**(q8 → bf16 を毎ステップ) |
| `mlp.down` | 93 ms | 逆量子化込みで **61 ms**(実測。密だけなら 46) |
| 1 ブロックの matmul 合計 | 255 ms | 約 200 + 逆量子化 50 = **約 250 ms** |
| attention | 17.3 | 17.2(同等) |
| 重みの置き場 | 28 ブロックを SSD からストリーミング、常駐 5.7 GB | bf16 なら 27 GB で**載らない**。GGUF q8 でも 13.6 GB 常駐 + 活性で、16GB では **M3 の結論(スワップ)と同じ** |

つまり MPS は「崖がない代わりに逆量子化を払う」ので matmul の合計はほぼ同額、attention は同じ、
そして**ブロック単位ストリーミングがないので 16GB に載らない**。neural accelerator は MLX の
q8 カーネルも既に使っている(M7、`affine_qmm_t_nax_*`)。**MPS の値はシリコンの天井を知るための
物差しとして使い、実装は MLX のまま `mlp.down` の崖を消す**、が正しい。

## 8. 踏んだもの

- mini の作業ツリーは `dcacf52` + 未コミットの変更で、M3 Pro の HEAD `5ca3c59`(M8c-f)と
  ずれている。今日の測定は合成テンソルなので影響しないが、**M9 の本番測定の前に揃えること。**
- torch を mflux の環境に入れないこと。`uv run --no-project --isolated --with torch` で足りる
  (Python 3.12 を指定。ダウンロード 121 MB、1 回だけ)。
- MPS の bf16 と fp16 は全形で同速。MLX は 2048³ で bf16 8.0 / fp16 13.1 と差が出るが、
  本番の形では出ない。
