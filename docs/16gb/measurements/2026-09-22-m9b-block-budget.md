# M9a / M9b: 本番の再現と、1 ブロック 320 ms の内訳を 1 プロセスで

- 測定日: 2026-09-22
- 機材: Mac mini (Apple M6) 16GB、macOS 27.0、MLX 0.32.0、GPU 独占
- 実装: `05a23e2`(M8d の最終構成。mini の作業ツリーをこのコミットに揃えてから測定)
- 再現: `tools/bench/block_budget.py --model ~/Library/Caches/mflux/16gb-bench/krea2-lowram`
  (実チェックポイントの block 0、bf16 活性、4126 トークン、ウォームアップ 3、8 回平均)
- 計画: [DiT を天井に近づける](../../.cursor/plans/2026-09-22-krea2-dit-ceiling.md) §M9a / §M9b

## 0. 結論

| | |
|---|---|

## 1. M9a: 本番の再現

```
Block streaming: 28 blocks, bind 0.5 ms + compute 320.7 ms + drop 0.2 ms per block,
next block read in 138.6 ms under the compute (compute/read 2.31)
steps: 9.05 / 9.01 / 8.99 / 9.00 s     peak MLX 4.43 GB, footprint 4.70 GB, verdict clean
```

M8d の記録(9.26 s、footprint 5.72 GB)より少し良い。ステップ時間の差は 2.7%、footprint の差は
swapwatch のサンプリング位置の違いと見る(判定には影響しない)。画像は M8d と完全一致
(`images/20260922-1633-m9a-m6mini-1024.png`、ログ `runs/m6mini/20260922-1633-m9a-1024.csv`)。

## 2. 鎖を 1 本ずつ伸ばす

8 本の matmul を単体で測った時間の累積(sum)と、ブロックと同じ順に鎖でつないだ時間(chain):

| 足した matmul | 単体 | 累積 | 鎖 | 隙間 |
|---|---|---|---|---|
| wq | 18.4 | 18.4 | 18.4 | 0.0 |
| + gate | 18.5 | 36.9 | 47.6 | **+10.7** |
| + wk | 4.8 | 41.7 | 52.0 | +10.3 |
| + wv | 4.8 | 46.5 | 56.8 | +10.3 |
| + wo | 18.5 | 64.9 | 79.6 | +14.7 |
| + mlp.gate | 48.9 | 113.8 | 127.2 | +13.4 |
| + mlp.up | 48.9 | 162.8 | 209.8 | **+47.0** |
| + mlp.down | 93.3 | 256.1 | 307.5 | +51.5 |

- 隙間は 2 本目で +10.7 開き、wk / wv では増えない。wo(50 MB の出力)で +4、mlp.gate で −1、
  **mlp.up で +33**。mlp.up は mlp.gate と同じ入力 `o` から 135 MB の出力をもう 1 つ作り、
  2 つが同時に生きる。
- 単体の測定は同じ出力バッファを使い回すので、隙間の候補は「同時に生きる大きな中間バッファの
  確保(ページフォルト)」か「独立な 2 本目のカーネル」。§3 で切り分ける。

## 3. 隙間の切り分け → **独立な matmul の並行ディスパッチ**

2 本の matmul を 1 つの eval に入れて、並べ方だけ変える(`--only gap`):

| 並べ方 | ms | 単体の和 | 差 |
|---|---|---|---|
| `wq(x)` | 18.5 | | |
| `[wq(x), gate(x)]` 独立、2 出力 | 45.8 | 37.0 | **+8.8** |
| `gate(wq(x))` 依存、1 出力 | **36.7** | 37.0 | **−0.3** |
| `wq(x) + gate(x)` 独立、加算で 1 出力 | 48.6 | 37.0 | +11.6 |
| `mlp.gate(o)` | 48.8 | | |
| `[mlp.gate(o), mlp.up(o)]` 独立 | **132.7** | 97.6 | **+35.1(+36%)** |
| `mlp.gate(o) + mlp.up(o)` | 135.8 | 97.6 | +38.2 |
| `silu(mlp.gate(o)) * mlp.up(o)`(ブロックの形) | 135.9 | 97.6 | +38.3 |
| `[mlp.gate(o), mlp.up(o)]`、cache limit 0 | 132.2 | | 変わらない |
| `[mlp.gate(o), mlp.up(o)]`、eval 毎に synchronize | 132.1 | | 変わらない |

- **依存でつながった 2 本は単体の和と一致し、独立な 2 本は和より 9〜38 ms 遅い。**
  バッファの確保(cache limit 0 で不変)でも、計測ループのパイプライン効果(synchronize 毎で不変)でもない。
- MLX の Metal バックエンドは依存のないカーネルを**並行にディスパッチ**する。q8 の nax カーネルは
  キャッシュに敏感(M9 §2 の K の崖と同根)なので、2 本が同時に走るとお互いのタイルを追い出して
  合計で遅くなる。ブロック内で独立なのは attention の 4 射影(wq / wk / wv / gate)と mlp の gate / up、
  そして K 分割の 4 片。**鎖の隙間 51 ms は全部これで説明がつく**(§2: gate で +10.7、mlp.up で +33)。
- **ただしこれは単体ペアの現象で、ブロックの中では起きていない**(§3b、M9c §3b)。ブロックの
  時間は matmul 単体和 + sdpa + 要素演算で閉じる。M8c の敗因は別(M9c: `async_eval` のブロック)。

## 3c. 単体ペアでの再検証(`--only gap2`): 実データ依存だけが直列化する

| 並べ方 | ms |
|---|---|
| `[gate(o), up(o)]` 独立 | 127.2 |
| `[gate(o), up(o2)]` 独立、入力は別コピー | 132.3 |
| **`up(o + 0 * g[..., :1])` 実データ依存(+要素演算 1 本 0.9 ms)** | **98.0**(単体和 97.6) |
| `up(mx.depends(o, g))` | 131.0(効かない) |
| `mx.async_eval(g)` してから `up(o)` | 129.0(効かない) |

Metal のバリアはバッファの書き手と読み手で決まるので、`mx.depends`(グラフだけの辺)も
`async_eval` の境界(コマンドバッファは並ぶ)も直列化しない。実データの依存だけが効く。
**ブロックに入れても効かなかった**(§3b)ので、ここは記録だけ。

## 3b. `mx.depends` で直列にする → **効かない**(GPU のバリアにならない)

| 構成 | ms | |
|---|---|---|
| block | 316.8 | |
| block, 1s(attention の 4 射影と mlp の gate/up を `mx.depends` で数珠つなぎ) | 315.9 | −0.9 |
| block, 4c(K4 分割、片は独立) | 277.0 | |
| block, 4cs(K4 分割、片も `mx.depends` で数珠つなぎ) | 275.8 | −1.2 |
| block, 4cs, norm bf16 weight | 275.6 | |
| 同じ 5 行を `MLX_BFS_MAX_WIDTH=1` で | 324 / 320 / 284 / 279 / 271 | 変わらない(むしろ +7) |

- `mx.depends` はグラフの依存を足すだけで、出力は入力のバッファをそのまま指す。Metal 側のバリアは
  **バッファの書き手と読み手**で決まるので、後続カーネルの入力バッファ(x)を書いたカーネルが
  いなければ並行のまま。**§3 の「並行ディスパッチ」説の検証としては不十分**で、実データの依存
  (`up(o + 0 * g[..., :1])` のような 1 本の要素演算)か `mx.async_eval` の境界で再検証する(§3c)。
- `MLX_MAX_OPS_PER_BUFFER=1`(1 カーネル 1 コマンドバッファ)は本番形で main:1 335 → 374 と
  **遅くなる**。コミットの回数が 60〜80 になるので、この手で直列化の効果は測れない。

## 4. ブロックに候補の修正を 1 つずつ当てる

| 構成 | ms | 差 | |
|---|---|---|---|
| block(いま) | 317.6 | | 本番の 320.7 と一致 |
| block, compiled | **350.3** | **+32.7** | M9d-2。融合したのに遅い |
| block, norm bf16 weight | **307.0** | **−10.6** | M9d-1 |
| block, norm bf16 weight, compiled | 326.3 | +8.7 | |
| block, norm f32 weight | 319.1 | +1.5 | 効かない(float32 の積と cast がそのまま残る) |
| block, norm f32 weight, compiled | 326.6 | +9.0 | |
| block, down K4 | **277.0** | **−40.6** | M9c |
| block, down K4, compiled | 311.8 | −5.8 | |
| block, down K4, norm f32 weight, compiled | 286.2 | −31.4 | |

- **compile は損。** 要素演算は融合されるはずだが、ブロック全体で +33 ms。compile が中間の
  バッファを別の形で持つか、融合カーネルの質の問題。理由は追っていない
  (本番は compile なしで走るので、そのまま採用しなければ済む)。
- norm の bf16 化は −10.6 ms = **0.3 s/step**。数値は §5。
- K4 は単体 −40.6 ms = 1.1 s/step。本番形での判定は M9c。

## 4b. 要素演算を小さい関数単位で compile する → **効かない**(`--only fuse`)

| 構成 | ms |
|---|---|
| block | 328.3 |
| block, `apply_rope` だけ compile | 325.5(−2.8) |
| block, `silu(g) * u` だけ compile | 328.1 |
| block, 変調 `(1+s)*n+sh` と残差 `x+g*y` を compile | 328.1 |
| block, norm + 変調 + 残差を 1 つに compile | **353.3(+25)** |
| block, 全部 | 347.7 |
| block, 全部 + norm bf16 | 337.8 |

- 要素演算 34 ms は、compile で融合してもほぼ動かない。RoPE だけ −3。
- **`mx.fast.rms_norm` を含む関数を compile すると +25 遅くなる。** M9b §4 のブロック全体 compile が
  +33 だったのはこれ。MLX 0.32 の compile は fast op の周りで損をする。
- **要素演算で取れるのは norm の bf16 化 −10 ms だけ。** 融合は不採用。

(このセッションのブロック基準値は 317 → 328 と動いている。連続測定で温度が乗る。比較は同一セッション内で。)

## 5. norm の bf16 化の数値(block 0 の prenorm、実 scale、入力は正規乱数)

| 変種 | max abs | mean abs | max rel | mean rel | 動いた要素 |
|---|---|---|---|---|---|
| bf16 weight(`rms_norm(x_bf16, (1+scale)_bf16)`) | 0.031 | 0.00077 | 1.39% | 0.18% | 33% |
| f32 weight(`rms_norm(x_bf16, None) * (1+scale)_f32` → bf16) | 0.031 | 0.00058 | 0.78% | 0.14% | 26% |

- bf16 の 1 ULP は相対 0.39〜0.78%。**どちらの変種も差は 1 ULP 級**(max abs 0.031 は値 4〜8 の
  領域の 1 ULP)。`(1 + scale)` 自体を bf16 に丸めると最大 0.39% 動く(min 0.051 / max 1.586)。
- 速いのは bf16 weight のほう(f32 weight は速度が出ない)。**採用するなら bf16 weight を画像で判定。**

## 6. 踏んだもの

- `mx.compile` した関数を計測ループに渡すときは引数を束ねる(最初の実行は `TypeError`)。
- `mx.fast.rms_norm` は `weight=None` を受け、入力 bf16 と重み float32 を混ぜると出力は
  float32 に昇格する(だから「f32 weight」変種は cast が残って速くならない)。
