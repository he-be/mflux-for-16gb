# M5b: text encoder を q8 にする → **採用**

- 測定日: 2026-09-22
- 機材: MacBook Pro M3 Pro 18GB、macOS 15.6、MLX 0.32.0
- 再現: `tools/bench/te_encode.py --quantize 8`
- 対象: Qwen3-VL-**4B**(bf16 8.05 GB)

## 0. なぜ測ることになったか(前提の訂正)

計画の「非目標」に **「TE の量子化」が入っていたが、根拠がなかった**ので取り下げた。

- ユーザからそういう要件は出ていない。fork 初回コミット `b01d4d7` で
  エージェントが勝手に足した行だった。
- 根拠にしていたのは upstream のコード内コメント 1 行
  (`krea2_weight_definition.py:52` の
  `skip_quantization=True,  # quantizing the TE degrades conditioning`)。
  **実測ではないし、どのビット幅で何がどう劣化するのかも書かれていない。**
- **q8 は DiT で受け入れている品質基準そのもの。** TE だけ一律で禁じるのは筋が通らない。

M5 の後、**パイプライン最大の消費は TE の 8.29 GB** になっていた。

## 1. 数字

| | bf16 | **q8** |
|---|---|---|
| `mx.get_active_memory()` | 8.05 GB | **4.28 GB**(-47%) |
| エンコード時間 | 0.63〜0.82 s | **0.41 s** |
| 量子化にかかる時間 | — | 0.73 s(1 回) |
| verdict | clean | **clean** |

ロード時のピークは 8.63 GB(footprint 12.08 GB)。bf16 を読んでから量子化するので、
一瞬だけ両方が同時に存在する。**これは一度 q8 で保存すれば消える**(§4)。

- **描き込みの密度は同等。** 腐食のピット、ボルトの頭、真鍮の質感、窓の結露、
  作業台の木目 — どれも落ちていない。
  q4 で問題になる「描き込みが減る」タイプの劣化ではない。

## 4. q8 の TE をチェックポイントに保存する → **実装して検証した**

`--quantize 8` は毎回 bf16 8.05 GB を読んでから量子化するので、
**ロード時に 12.08 GB の一時ピーク**が出る。`tools/bench/quantize_te_checkpoint.py` で
1 回だけ量子化して保存するようにした(LoRA 焼き込みと同じ、層単位のやり方)。

### 作るとき

| | |
|---|---|
| mx peak memory | **1.19 GB** |
| 所要時間 | **2.3 秒**(36 層 + embed + norm) |
| ディスク | 4.27 GB(元の bf16 は 8.05 GB) |
| verdict | **clean** |

出力は mflux のスナップショットと同じ配置(`text_encoder/` + `tokenizer/`)なので、
そのまま `--model` に渡せる。

### 読むとき

| | `--quantize 8`(その場で量子化) | **q8 チェックポイント** |
|---|---|---|
| `mx.get_active_memory()` | 4.28 GB | **4.28 GB** |
| mx peak | 8.63 GB | **4.47 GB** |
| **実 footprint** | **12.08 GB** | **4.96 GB** |
| materialize | 1.30 s | **0.49 s** |
| encode | 0.41 s | **0.13 s** |

**埋め込みは 2 経路でビット完全一致。**

### 踏んだ罠: `nn.quantize` はルートモジュール自身を置換できない

最初の版は `nn.quantize(encoder.embed_tokens, ...)` のように**部分モジュールを
直接渡していた**。`nn.quantize` はそのモジュールの**子**を置き換えるので、
渡したモジュール自身が量子化対象のときは**何も起きない**。結果:

- `embed_tokens`(151936×2560)が bf16 のまま保存され、
- チェックポイントは 4.64 GB(正しくは 4.27 GB)、
- 埋め込みがその場で量子化した版と一致しない(max abs diff 10.0)。

**気づけたのは 2 経路を突き合わせたから。** 量子化された層の数を数えると
252 対 253 で、差分は `embed_tokens.scales` だった。

直し方は、**評価前にエンコーダ全体を 1 回で量子化する**こと。`mx.quantize` は遅延なので
これでコストは増えない(その後に層単位で eval して書き出す)。

## 5. パイプラインへの効果

| 段 | 変更前 | 変更後 |
|---|---|---|
| **text encoder** | **8.29 GB** ← 最大 | **4.96 GB**(常駐 4.28 GB) |
| LoRA 焼き込み(1 回だけ) | 2.14 GB | 2.14 GB |
| DiT ストリーミング | 3.72 GB | 3.72 GB |
| VAE(タイル 256) | 4.28 GB | 4.28 GB |

1 回だけ必要な前処理(どちらも clean):

| | mx peak | 時間 |
|---|---|---|
| TE の量子化 | 1.19 GB | 2.3 s |
| LoRA の焼き込み | 1.89 GB | 13 s |

**パイプライン全体の最大消費が 8.29 → 4.96 GB になった。**
どの段も 5 GB を超えない。16GB 機に対して大きな余裕がある。
