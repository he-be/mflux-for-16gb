# M3: q8 DiT + 4step LoRA (14.06 GB) を 18GB 機に常駐させられるか

- 測定日: 2026-09-22
- 機材: MacBook Pro M3 Pro 18GB、macOS 15.6、MLX 0.32.0
- 再現: `tools/bench/dit_steps.py`(`tools/swapwatch.py` 越し)
- 前提条件: [M1 のベースライン](2026-09-22-m1-clean-baseline.md)
- 対象: q8 DiT 13.62 GB + 4step LoRA 0.44 GB、1024²、4 ステップ、`euler`、guidance 1.0、seed 42

**この文書は段を進めるたびに追記している。**(実験中にマシンごと落ちる可能性が
あるため、各段の結果は次の段を始める前に書き出してコミットする。)

## 段の一覧(計画の無理のかけ方)

| 4 | `--width 768 --height 768` | **意味がない**(下の常駐下限の節) |

## 段 1: そのまま → **不合格 (SWAPPED)**

- 実行: `20260922-0900`、`docs/16gb/runs/20260922-0900-m3-dit-step1.csv`
- 開始時の状態: swap 0 MB、compressor 0.73 GB、free 8.23 GB、claimable 11.96 GB

swapwatch のサンプル(1 秒間隔):

| t | swap 増分 | compressor | footprint | swapouts |
|---|---|---|---|---|
| 0.1 s | 0 | 0.73 GB | 0.01 GB | 0 |
| 1.2 s | 0 | 0.73 GB | 0.21 GB | 0 |
| 3.5 s | 0 | 2.14 GB | **7.75 GB** | 0 |
| 5.0 s | **1370 MB** | **13.31 GB** | **13.33 GB** | **85088 ページ (1394 MB)** |

**判定: SWAPPED。** swapwatch が既定の閾値(+1024 MB)で実行を落とした。

### どこで落ちたか

footprint 13.33 GB は **DiT のウェイト実体化の途中**(13.62 GB の手前)。
LoRA の適用にも、1 ステップ目にも到達していない。つまり

> **アクティベーションの話をする前に、ウェイトを置くだけで足りていない。**

### compressor の動き方が示していること

compressor が 0.73 → 2.14 → **13.31 GB** と、footprint とほぼ同じ速さで伸びている。
OS は MLX に 13.62 GB を渡すために他のページを圧縮し続け、圧縮しきれなくなった
時点でスワップアウトを始めた。free 8.23 GB / claimable 11.96 GB は
**13.62 GB には足りなかった**。

### 疑っていること(まだ未検証)

ウェイトを読む経路は `mx.load` → `mx.eval` で、**ページキャッシュを迂回していない**。
13.62 GB のファイルを読むと、その分のファイルバックのページもキャッシュに載る。
つまりこの瞬間、

- MLX の Metal バッファ: 最大 13.62 GB
- 同じ内容のページキャッシュ: 最大 13.62 GB(クリーンなので回収可能だが、
  OS は先に匿名ページの圧縮 → スワップを選ぶことがある)

が同時に存在しうる。M0 の読み出しベンチは `F_NOCACHE` を使ってこれを避けていたが、
`mx.load` は使わない。**これが主因かどうかは切り分けが必要**(段 2 では変わらない、
段 3 でも変わらない → 切り分けるには読み出し側に手を入れる必要があり、
それは M5 / M6 の作業になる)。

## 段 2: MLX のキャッシュを絞る → **不合格 (SWAPPED)**

- 実行: `20260922-0903`、`--cache-limit-gb 1 --clear-cache-each-step`
- 記録: `docs/16gb/runs/20260922-0903-m3-dit-step2.csv`
- 開始時の状態: **claimable 13.73 GB / free 11.13 GB**(段 1 の 11.96 GB より広い。
  段 1 の中断がページキャッシュを一掃したため)

| t | swap 増分 | compressor | footprint |
|---|---|---|---|
| 0.1 s | 0 | 0.43 GB | 0.01 GB |
| 1.2 s | 0 | 0.43 GB | 0.15 GB |
| 2.6 s | 0 | 0.43 GB | 5.33 GB |
| 4.1 s | 0 | 6.29 GB | 11.28 GB |
| 5.4 s | **2164 MB** | 10.66 GB | **13.33 GB** |

**判定: SWAPPED。段 1 より悪い**(スワップアウト 2267 MB、段 1 は 1394 MB)。

### 分かったこと

**キャッシュ上限は効かない。** 落ちた場所は段 1 と同じ footprint **13326 MB**
(両段とも同値)。`mx.set_cache_limit` が制限するのは MLX が解放済みバッファを
再利用のために抱える分で、いま問題になっているのは**ウェイトそのもの**だから、
効かないのは筋が通っている。`--clear-cache-each-step` に至ってはステップループまで
到達していないので、そもそも一度も呼ばれていない。

### 開始時の空きが広くても結果は変わらなかった

段 2 は段 1 より 1.77 GB 広い状態(claimable 13.73 GB)から始めて、**より多く
スワップした**。13.62 GB を置くには、claimable が 13.73 GB あっても足りない。
ファイルを読む側のページキャッシュが同時に要る、という疑いを補強する材料ではあるが、
これだけでは確定しない。

### この 2 段で確定したこと

**アプリ側(MLX の API)の調整では届かない。** 次は OS 側の設定
(`iogpu.wired_limit_mb`)に手を入れる段 3。

## 段 3a: `iogpu.wired_limit_mb` を 14336 に上げる → **不合格 (SWAPPED)**

`sudo sysctl -w iogpu.wired_limit_mb=14336` を実行(ユーザが手動)。効果は出ている:

| | 既定 (0) | 14336 |
|---|---|---|
| `max_recommended_working_set_size` | 12.88 GB | **15.03 GB** |

この状態で、**wire での固定はせずに**(`--wired-limit-gb` なし)回した。

- 実行: `20260922-0906`、記録: `docs/16gb/runs/20260922-0906-m3-dit-step3a.csv`
- 開始時: claimable 13.71 GB、swap 既使用 619 MB、compressor 0.18 GB

**判定: SWAPPED。** スワップアウト **3169 MB**(段 1 は 1394、段 2 は 2267)。
working set が 14.06 GB より広くなっても結果は変わらなかった。

## ここまでの 3 段で分かった一番大事なこと

### footprint は毎回きっかり 13326 MB で止まる

| 段 | 開始時 claimable | スワップアウト | **peak footprint** |
|---|---|---|---|
| 1 | 11.96 GB | 1394 MB | **13326 MB** |
| 2 | 13.73 GB | 2267 MB | **13326 MB** |
| 3a | 13.71 GB | 3169 MB | **13326 MB** |

条件も落ちた時刻(t = 5.0 / 5.4 / 5.0 s)も違うのに、**3 回とも 1 MB 単位で同じ値**。
サンプリングの偶然ではありえないので、内訳を計算した:

```
transformer の 7 シャードの実バイト数 = 13,622,825,753 B = 12992 MiB
観測された footprint の頭打ち                            = 13326 MiB
差                                                      =   334 MiB  (python + MLX + 埋め込み)
```

**一致した。** つまりこれは確保の上限ではなく、**ウェイトが最後まで載りきった状態**。

### 読み方が変わる

「13.62 GB は確保できない」ではない。**確保はできている。**
できているが、その場所を作るために OS が他のページを 1.4〜3.2 GB スワップアウトしている。

- swapins は 60〜428 ページしかない = **追い出されているのは自分のページではない**
  (自分のウェイトが追い出されていれば、使うたびに大量の swapin が出る)。
- 追い出されているのは他プロセスの冷たいページ。OS が 13.97 GB 分の場所を
  作るために掃き出している。

### まだ分かっていない: 一過性か、継続的な thrash か

swapwatch は既定の閾値(+1024 MB)で、**ロードの最中に**実行を落としている。
4 ステップには一度も到達していない。したがって

- ロード中の一過性のスワップで、その後は定常状態に落ち着くのか
- それとも掃き出し続けるのか

が区別できていない。**この区別は重要**で、前者なら読み出し側(ページキャッシュを
迂回する = M5 / M6 の作業)で消せる見込みがあるが、後者なら単に載らない。

区別するには閾値を上げて、ロードを最後まで通す必要がある。次はそれを測る。

## 常駐の下限を分離する(`--load-only`)

段 1〜3a はどれも**ロードの途中で**落ちていて、4 ステップに一度も到達していない。
そこで `tools/bench/dit_steps.py --load-only` を足した。ウェイトを載せて、
ステップを回さず、そのまま `--hold-seconds` 秒座っているだけのモード。
測りたいのは一点:

> **13.62 GB のウェイトは、何もしなくても、ただ置いておけるのか。**

### 実行: LoRA なし、ステップなし、10 秒座るだけ

- 実行: `20260922-0909`、記録: `docs/16gb/runs/20260922-0909-m3-loadonly-nolora.csv`
- **これまでで一番広い開始条件**: claimable **14.20 GB**、free 11.97 GB、
  compressor 0.09 GB、`iogpu.wired_limit_mb=14336`(working set 15.03 GB)

プロセス内から見た値(子プロセスの出力を初めて拾えた):

```
DiT resident      : active 13.62 GB, peak 13.62 GB
```

**MLX が握っているのはウェイトちょうどで、余分は一切ない。**
量子化のやり直しにも `model.update` にも一時バッファの無駄はなかった。

| t | swap 増分 | compressor | footprint |
|---|---|---|---|
| 0.1 s | 0 | 0.09 GB | 0.02 GB |
| 1.2 s | 0 | 0.09 GB | 2.23 GB |
| 2.7 s | 0 | 2.62 GB | 9.96 GB |
| 4.2 s | **594 MB** | 10.20 GB | 12.30 GB |
| 5.4 s | **2908 MB** | 9.90 GB | 13.33 GB |

**判定: SWAPPED。3058 MB 掃き出した。** 10 秒座るところまで行っていない。

### これで確定したこと

**このマシンでは、q8 DiT のウェイト 13.62 GB を「置くだけ」ができない。**

- LoRA (0.44 GB) は関係ない。**外しても落ちる。**
- アクティベーションは関係ない。**1 ステップも回していない。**
- 解像度は関係ない。**768² に落としてもウェイトの 13.62 GB は変わらない。**
  → **計画の段 4(768² に落とす)は測る意味がない。**
- 空きメモリの問題でもない(claimable 14.20 GB > 13.62 GB で始めて落ちた)。
- `iogpu.wired_limit_mb` を上げて working set を 15.03 GB にしても変わらない。

### 疑い(次に測る): ページキャッシュが二重に要る

swapouts に対して swapins は 636 ページしかない。追い出されているのは自分のウェイト
ではなく、**他のページ**。compressor は footprint より先に 10.20 GB まで伸びている。

`mx.load` はページキャッシュを迂回しない。13.62 GB のファイルを読むと、

| | |
|---|---|
| MLX の Metal バッファ | 13.62 GB |
| 同じ内容のページキャッシュ(file-backed) | 最大 13.62 GB |
| 合計の瞬間需要 | **最大 27 GB**(RAM は 19.33 GB) |

が同時に立つ。これが正しければ、**読み出し側でページキャッシュを迂回すれば
13.62 GB だけで済み、claimable 14.20 GB に収まる**。

確かめるために `vm_stat` の **File-backed pages** を `swapwatch` と `memstat` に
追加した。ロード中にこれが 13 GB 級に膨らめば仮説は正しい。

---

## ページキャッシュ仮説 → **外れ**

同じ `--load-only` を、`vm_stat` の File-backed pages を追いながら 0.5 秒間隔で回した。

- 実行: `20260922-0910`、記録: `docs/16gb/runs/20260922-0910-m3-loadonly-pagecache.csv`

| t | footprint | **file-backed** | swap 増分 |
|---|---|---|---|
| 0.1 s | 0.01 GB | 2.81 GB | 0 |
| 1.3 s | 0.21 GB | 2.92 GB | 0 |
| 2.0 s | 4.13 GB | **6.47 GB** | 0 |
| 3.0 s | 9.12 GB | **6.71 GB** ← 山 | 0 |
| 4.2 s | 11.28 GB | 3.47 GB ← 回収されている | 0 |
| 4.9 s | 13.33 GB | 2.25 GB | **1387 MB** |

**仮説は外れ。** ページキャッシュは +3.9 GB しか伸びず(山は 6.71 GB)、こちらの
footprint が育つにつれて **OS が正しく回収している**。「13.62 GB のバッファ +
13.62 GB のページキャッシュ = 27 GB の瞬間需要」は起きていない。

したがって **読み出しで `F_NOCACHE` を使っても、この失敗は消えない。**
消せるのは山の 3.9 GB 分の一時的な圧力だけで、しかもそれは OS が既に回収している。

### 補足: compressor の数字は信用しない

`vm_stat` の「Pages occupied by compressor」は、実行中に 11.57 GB まで伸びたと
報告する。しかし同時刻の footprint 13.33 + file-backed 2.25 + wired 1.95 だけで
17.5 GB あり、物理 19.33 GB に 11.57 GB 分の余地はない。**この値は額面どおり
受け取れない**(phys_footprint が自分の圧縮済みページを二重に数えている可能性が
ある)。

**以降、compressor の値を結論の根拠に使わない。** 根拠に使うのは相互に整合が
取れている 4 つだけ: `mx.get_active_memory()` / `phys_footprint` /
swapouts・swapins / file-backed。

## 段 3b: `mx.set_wired_limit` でウェイトを固定する → **合格 (clean)**

- 実行: `20260922-0912`、記録: `docs/16gb/runs/20260922-0912-m3-loadonly-wired.csv`
- `--no-lora --load-only --hold-seconds 10 --wired-limit-gb 14`
- 前提: `iogpu.wired_limit_mb=14336`(これがないと MLX は 14 GB を wire できない)

```
mx peak memory    : 13.62 GB
mx active memory  : 13.62 GB
mx cache memory   : 0.00 GB
materialize       : 2.10 s
verdict           : clean   (swapouts 0、swap 増分 0)
```

| t | footprint | file-backed | swap 増分 | swapouts |
|---|---|---|---|---|
| 0.1 s | 0.01 GB | 3.03 GB | 0 | 0 |
| 2.0 s | 4.41 GB | 5.49 GB | 0 | 0 |
| 3.0 s | 10.25 GB | 4.82 GB | 0 | 0 |
| 4.0 s | **13.33 GB** | 1.46 GB | 0 | 0 |
| 4.8〜13.4 s | **13.33 GB(完全に平ら)** | 1.27 GB | **-16 MB** | **0** |

**10 秒間、1 ページも掃き出さずに座っていられた。** swap はむしろ 16 MB 減った。

### なぜ効いたのか

wire ありと wire なしで、OS の逃げ方が変わる:

| | wire なし(段 1〜3a) | wire あり(段 3b) |
|---|---|---|
| file-backed の山 | 6.71 GB → 2.25 GB | 5.49 GB → **1.27 GB** |
| 匿名ページの圧縮 | 大量 | ほぼなし |
| swapouts | 1394〜3169 MB | **0** |

wire していないと、MLX の Metal バッファは OS から見てただの匿名メモリなので、
**OS は場所を作るときにそれ自身を圧縮の候補にする**。13.62 GB を圧縮しようとして
行き詰まり、最後にスワップへ逃げる。

wire すると、そのバッファは回収対象から外れる。OS に残る手は**クリーンな
ファイルバックのページを捨てること**だけになり、実際 5.49 → 1.27 GB まで
ページキャッシュを手放して場所を作った。**捨てられるものを捨てるのが正解**であって、
圧縮もスワップも必要なかった。

### これが計画にとって意味すること

計画は `mx.set_wired_limit` を「段階 3 = 最後の手段」に置いていた。**逆だった。**
これは最後の手段ではなく、**18GB 機で q8 DiT を常駐させるための唯一の手段**。
段 1・2・3a がすべて同じところで落ちていたのは、どれも wire していなかったから。

必要な設定は 2 つで、両方要る:

1. `sudo sysctl -w iogpu.wired_limit_mb=14336`(既定 0 のままでは MLX が wire できない。
   再起動で消える)
2. プロセス内で `mx.set_wired_limit(14 * 1e9)`

### まだ確かめていないこと

- **LoRA を足した 14.06 GB でも通るか**(いまのは 13.62 GB)
- **4 ステップ回したときのアクティベーション込みで通るか**(いまは 1 ステップも
  回していない)

## LoRA を足す → **惜しい (SWAPPED 82 MB)**、ただし数字の理解が変わった

- 実行: `20260922-0913`、`--load-only --hold-seconds 10 --wired-limit-gb 14.5`
- 記録: `docs/16gb/runs/20260922-0913-m3-loadonly-lora-wired.csv`

```
materialize       : 2.10 s
lora (bake 込み)  : 6.69 s
mx peak memory    : 15.23 GB   ← bake 中の一時ピーク
mx active memory  : 13.62 GB   ← bake 後の常駐
verdict           : SWAPPED (82 MB / 5008 ページ、swap 増分 70 MB)
peak footprint    : 14.35 GB
```

### 計画の前提が 1 つ間違っていた

**「DiT + 4step LoRA = 14.06 GB が常駐する」は誤り。**

LoRA は q8 のウェイトに**焼き込まれる**ので、bake 後の常駐は **13.62 GB のまま**。
0.44 GB は足されない。足されるのは常駐ではなく、**bake 中の一時ピーク**:

| | |
|---|---|
| bake 前・後の常駐 | 13.62 GB |
| **bake 中のピーク** | **15.23 GB**(+1.61 GB) |

つまり通すべき山は 14.06 GB ではなく **15.23 GB** で、しかもそれは一瞬だけ。
`iogpu.wired_limit_mb=14336`(= 14336 MiB = **15.03 GB**)をわずかに超えている。

なお `iogpu.wired_limit_mb` の単位は **MiB** だと確認できた:
14336 MiB = 15,032,385,536 B で、`max_recommended_working_set_size` の実測値と
1 バイトまで一致する。

### 落ち方は段違いに軽い

| | swapouts |
|---|---|
| 段 1(wire なし) | 1394 MB |
| 段 3a(wire なし、working set 拡大) | 3169 MB |
| **LoRA + wire あり** | **82 MB** |

wire が効いている状態で、bake の一時ピークだけが 15.03 GB の枠をはみ出している。

### 次に試すこと

1. **`--no-bake-lora` 相当**。LoRA を焼き込まず別レイヤのまま持つと、常駐は
   13.62 + 0.44 = 14.06 GB に増えるが、**bake の 15.23 GB のピークが消える**。
   15.03 GB の枠に収まる見込み。
2. それでも駄目なら `iogpu.wired_limit_mb` をもう一段上げる。
