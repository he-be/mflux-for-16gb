## 段 1: そのまま → **不合格 (SWAPPED)**

- 実行: `20260922-0900`、`docs/16gb/runs/20260922-0900-m3-dit-step1.csv`
- 開始時の状態: swap 0 MB、compressor 0.73 GB、free 8.23 GB、claimable 11.96 GB

swapwatch のサンプル(1 秒間隔):

| t | swap 増分 | compressor | footprint | swapouts |
|---|---|---|---|---|
| 0.1 s | 0 | 0.73 GB | 0.01 GB | 0 |
| 1.2 s | 0 | 0.73 GB | 0.21 GB | 0 |
| 3.5 s | 0 | 2.14 GB | **7.75 GB** | 0 |
| 5.0 s | **1370 MB** | **13.31 GB** | **13.33 GB** | **85088 ページ (1394 MB)** |

**判定: SWAPPED。** swapwatch が既定の閾値(+1024 MB)で実行を落とした。

### どこで落ちたか

footprint 13.33 GB は **DiT のウェイト実体化の途中**(13.62 GB の手前)。
LoRA の適用にも、1 ステップ目にも到達していない。つまり

> **アクティベーションの話をする前に、ウェイトを置くだけで足りていない。**

### compressor の動き方が示していること

compressor が 0.73 → 2.14 → **13.31 GB** と、footprint とほぼ同じ速さで伸びている。
OS は MLX に 13.62 GB を渡すために他のページを圧縮し続け、圧縮しきれなくなった
時点でスワップアウトを始めた。free 8.23 GB / claimable 11.96 GB は
**13.62 GB には足りなかった**。

### 疑っていること(まだ未検証)

ウェイトを読む経路は `mx.load` → `mx.eval` で、**ページキャッシュを迂回していない**。
13.62 GB のファイルを読むと、その分のファイルバックのページもキャッシュに載る。
つまりこの瞬間、

- MLX の Metal バッファ: 最大 13.62 GB
- 同じ内容のページキャッシュ: 最大 13.62 GB(クリーンなので回収可能だが、
  OS は先に匿名ページの圧縮 → スワップを選ぶことがある)

が同時に存在しうる。M0 の読み出しベンチは `F_NOCACHE` を使ってこれを避けていたが、
`mx.load` は使わない。**これが主因かどうかは切り分けが必要**(段 2 では変わらない、
段 3 でも変わらない → 切り分けるには読み出し側に手を入れる必要があり、
それは M5 / M6 の作業になる)。
