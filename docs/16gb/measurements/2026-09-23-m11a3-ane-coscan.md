## 0. 結論

M11a は「本番の横で ANE を回すと GPU が 2.16 倍遅くなる」で止まっていた。その同居人は **`mlp57` = gate/up + silu·mul + down** だった。
同居人の中身と GPU 側のカーネルを振って測り直すと、**損の大半は down(K が大きい行列積)を ANE に載せたことに由来**し、
gate/up だけなら GPU の損は 2 割で、**ANE が足す分のほうが大きい**。

| | |
|---|---|
| **`mlp57`(down 込み)を横で回す** | GPU 16.99 → **6.74 TFLOPS(−60%)**、ANE 9.5 TOPS。**合計 16.3 < 単独 17.0**(M11a の再現) |
| **`gateup57`(gate/up + silu·mul、down なし)を横で回す** | GPU 16.99 → **13.64(−20%)**、ANE **10.4** TOPS。**合計 24.0 = 単独の 1.41 倍** |
| `gate`(gate だけ)を横で回す | GPU −15%、ANE 9.4。合計 23.8 |
| **ANE の 1 TOPS に GPU が払う TFLOPS(価格)** | gate/up 系 **0.27〜0.32**、`mlp57` **1.07**、`down` 単体 **1.01** |

**M11a の「ANE 併用は割に合わない」は `mlp57` という同居人についてだけ正しかった。** gate/up を ANE、down を GPU に残す分割なら
足し算は成り立ち、合成では 1.4〜1.6 倍。ただし **1 ブロック実物では −4〜−5%** で、受け渡しと直列の尾が合成の利得の大半を食っている(§6)。
常駐は +3〜4 GB。**これを採るかは数字を見て決めること**で、この文書は合否を引かない。

## 1. クロックについて(M11a §13 の読み直し)

M11a §13 は併走時に GPU のクロックが 1660 → 1408 MHz(0.85 倍)、速度が 0.46 倍と報告した。今回の格子から言えること:

- **クロックの落ち(0.85)では速度の落ち(0.46)は説明できない。** 残りの 0.54 は 1 サイクルあたりの仕事が減った分 = **GPU がストールしている**。
  電力 0.42 倍(§13)は「サイクル 0.85 × 1 サイクルの活動 0.54 × 電圧の分」でほぼ合う。
- **同じ同居人でも GPU 側のカーネルで損が違う**(sdpa −19% / q8 −60% / 密 −61%)。SoC 全体のクロック上限なら
  カーネルによらず同じ率で落ちるはずなので、**クロックが主因ではない**。
- 演算しない同居人(`dma`)でも 1 割落ち、CPU で回しても 16% 落ちる。**ANE が(あるいは CPU が)メモリ系を叩くこと自体が GPU をストールさせ**、
  クロックはそれに追随して下がっている、と読むのが数字に合う。ただし機構(SLC / ファブリック / QoS のどれか)はこの測定では決まらない。

つまり「クロックを戻す」ハックは筋が悪い(sudo なしに触る手段もない)。効いたのは **ANE に渡す仕事の形を変えること**だった。

## 2. 方法: `coscan`

GPU 側のカーネルを 1 種類ループで回し(0.4 秒ごとに epoch 付き TFLOPS を出力)、その横で ANE の同居人を別プロセスで回す
(同じく epoch 付き TOPS)。重なった区間(先頭 1.5 秒を捨てて 12 秒)の両方の平均を取る。

- **価格** = (GPU 単独 − GPU 併走) ÷ ANE 併走 TOPS。**1.0 未満なら、2 台合わせた演算量が GPU 単独を上回る**。
- GPU カーネル: `q8gate`(本番の 6144→16384 q8、M=4126)、`sdpa`(48/12 ヘッド、L=4126)、`dense`(4096³ bf16)
- 同居人(すべて M=4126、int8 行スケール、fp16 活性、`NeuralEngine` に載ったことを compute plan で確認):
  - `gate` 6144→16384(100 MB)、`wq` 6144→6144(38 MB)、`down` 16384→6144(101 MB)
  - `mlp57` = gate/up 57% 列 + silu·mul + down(K=9344)(172 MB)。M11a の候補
  - **`gateup57`** = gate/up 57% 列 + silu·mul、**down なし**(115 MB)。出力は h の 57% 列(4126×9344 fp16 = 77 MB)
  - `gateup25` = 同 25% 列(50 MB)
  - `dma` = y = 1.5x + 0.5 を (4126, 16384) fp16 に(重みなし、135 MB 入 / 135 MB 出)
  - `gate` を **CPU_ONLY** で(BNNS。ANE を使わない対照)
- デューティ: 4 回の predict ごとに `busy × (1−d)/d` 眠る。窓は眠りを含むので TOPS は時間平均

読み方:

- **同居人が down を含むかどうかで、行列積カーネルの損が −20% と −60% に分かれる。** `gateup57` と `mlp57` は
  重みが 115 MB と 172 MB、ANE の TOPS はほぼ同じ(10.4 / 9.5)なのに、GPU の損は 3 倍違う。
- `down` 単体でも価格 1.01。**ANE は K の大きい行列積が単独でも遅く(3.6 TOPS)、その間 GPU も 2 割落ちる**ので、
  どう組んでも down を ANE に載せる形は足し算にならない。`mlp57` の −60% は gate/up(−20%)と down(−20%)の
  足し算より大きく、融合した 1 モデルの中で中間テンソル(77 MB)を持ち回る分が上乗せされていると考えられる(未測定)。
- **sdpa は何が来ても平気**(−7〜−19%)。sdpa はオペランドが小さく演算密度が高い。**同居人にやられるのは
  メモリ系に依存する行列積カーネル**で、q8 も密 bf16 も同じ。
- CPU だけで回しても −16%、演算なしの `dma` でも −11%。**GPU が落ちる主因は ANE の演算ではなく、同居人がメモリ系に出す
  トラフィック**。この 1〜2 割は gate/up 系の同居人が払う「基本料」で、down 込みはその上に別の 4 割が乗る。

## 6. 分割にしたときの見積り(gate/up を ANE、down は GPU)

計画 §2 の分割から **down を GPU に戻す**:

1. attention の後、MLP 入力 x(4126×6144 fp16、51 MB)を ANE に送る
2. **ANE**: 自分の列 a の gate/up + silu·mul → h_ane(4126 × 16384a fp16)を返す
3. **GPU(ANE と並行)**: 残りの列 (1−a) の gate/up + silu·mul → h_gpu、続けて **down の K 分割の自分の分** y = h_gpu · W_down[:, gpu 列]ᵀ
   (`down_splits` の部分和と同じ積算。ANE の答えを待たずに進められる)
4. h_ane が戻ったら y += h_ane · W_down[:, ane 列]ᵀ(GPU、51a ms)

1 ブロックの単独 compute 335 ms(`stream_ab main:1`)のうち MLP は gate/up 98 + down(K4)51 = 149 ms(M8 §2)。

- ANE の時間: 1.66a TFLOP ÷ 10.4 TOPS(併走時)= **160a ms**
- GPU の独立な仕事: 149(1−a) ms、ANE の間は 0.8 倍で走るので **186(1−a) ms**
- 釣り合い: 186(1−a) = 160a → **a ≈ 0.54、86 ms**。その後 down の残り 51 × 0.54 = 28 ms、受け渡し 8 ms(M11a §8 の 3.5 ms + 77 MB の copy-out)
- **MLP 149 → 約 122 ms、1 ブロック 335 → 約 308 ms(−8%)。1 ステップ 9.4 → 約 8.6 s**

これは合成の価格(0.32)で引いた数字。本番の横で回したときの価格は §5 で 0.29 と出た。常駐は package 28 × 115 MB ≈ **3.2 GB** +
Core ML ランタイム 0.7〜0.9 GB(M11a 基準 4 の実測)。いまの footprint 5.3 GB(1024²)/ 6.5 GB(1280²)に足すと **9〜10.5 GB**。
M7 の claimable 12.45 GB の内側だが VAE の 14 GB ピークとは別に見ること。

- ベースラインが戻りで +7〜10% ずれる(§8 のドリフト)。表の比率は先頭の alone4 に対して。

### 6-2. 伸ばす余地

1. **行方向のパイプライン**(`ane57:1:2` = 行を 2 分割して 2 回 predict、前半の h_ane が戻った時点でその down を流す)→ **§6-3、効かない**。
2. ~~ANE 側を 2 プロセスにする~~: **合計が増えない**(§0 の表。ANE +1.3 TOPS に GPU −11% を払う)。
3. int8 活性: 上の表。速度は取れるが画像判定が先。

### 6-3. 行方向のパイプラインは効かない

M = 2063 の package を作り(ANE 単独 15.1 TOPS、a8 19.9。M = 4126 と同じ)、1 ブロックの 4126 行を 2 回の predict に分けた。
前半が戻った時点でその行の down を GPU に投げる。

| 構成 | 1 ブロック | 対 alone4 | 先頭が戻るまで | 最後の down を投げるまで | predict 合計 |
|---|---|---|---|---|---|

| ane57(1 回) | 272.2 | −0.9% | 101.9 | 103.9 | 98.3 |

### 6-4. この分割の天井

1 ブロックの MLP = max(GPU 側の独立な仕事, ANE の窓)+ 直列の尾。実測から:

- GPU 側: 149(1−a) ms、ANE の間は 0.8 倍 → 186(1−a)
- ANE の窓: fp16 活性 160a ms(併走 10.4 TOPS)、a8 **117a**(14.2 TOPS)
- 尾: ANE の列の down(a × 51 ms、K が 8192 を超えると M9 の崖で 1.5 倍)+ h_ane の変換 ≈ 10 ms
- 固定費: MLP 入力の eval(ブロック途中の同期)+ 51 MB の copy ≈ 5〜10 ms

| | a | MLP(alone4 は 151) | 1 ブロック(276) |
|---|---|---|---|
| fp16 活性、実測(ane57) | 0.57 | 141 | **−3.7%** |
| fp16 活性、a を釣り合いに寄せた理想 | 0.45 | 102 + 23 + 10 = 135 | **約 −6%** |
| a8、実測 | 0.57 | 138 | **−4.9%** |
| a8、理想 | 0.50 | 93 + 25 + 10 = 128 | **約 −8%** |

**合成の「合計 1.4〜1.6 倍」が 1 ブロックで 1 桁 % になる理由は 2 つ**: (1) ANE に渡せる仕事は MLP の gate/up だけで、
ブロックの 3 分の 1(attention と down の間)しか窓がない。(2) ANE の答えを使う down は ANE の後ろに直列で残り、
GPU 側の独立な仕事とは重ならない。attention の projection を ANE に出す案は、ANE の wq が GPU の 18 ms に対し 31 ms かかる(§3 の 10 TOPS)ので
取り分が 3 分の 1 以下になり、同期 1 回ぶんも稼げない。

**1 ステップに直すと 9.4 → 約 9.0 s(実測ぶん −4〜−5%)、理想の実装で約 8.7 s(−8%)。** 代償は常駐 +4 GB(package 3.2 GB + Core ML ランタイム)、
worker プロセス、gate/up の行スケール再量子化(画像判定が必要)、28 package のコンパイル(初回 1〜4 分 × 28)。

## 8. 踏んだもの

- **GPU 単独が実行のたびに下がる。** 同じ `q8gate` ループが 16.99 → 14.09 → 14.70、sdpa が 14.47 → 13.76。M11a §2 のベースラインのドリフト
  (7.84 → 8.7 s/step)と同じ現象で、サーマル圧は Nominal のまま。**比率は同じ実行の中の単独と比べること**。格子は 1 実行の中で単独 → 同居人の順に
  測っているので比率は保たれている。
- `dma` の変換名を `row` で作って `fp16` で呼び、1 本目の格子では skip された(2 本目で取り直し)。
- mini の `audiomxd` が CPU 72%、`configd` が 42% で常時走っている(uptime 17 時間で 758 分)。ベースラインは M9c と一致するので今回の
  数字には効いていないが、CPU 側の同居人(`gate` を CPU で)の 3.5 TOPS はこの負荷込み。
