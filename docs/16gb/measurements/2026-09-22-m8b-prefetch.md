## 1. 方式

3 案を実ブロックで試作して選んだ(1024²、bf16、1 ブロック):

| 方式 | 合計 | 備考 |
|---|---|---|
| 直列(M8a まで) | 136 + 319 = **455 ms** | |
| **A: `mx.async_eval(out)` → 次を読んで `mx.eval` → `mx.eval(out)`** | **328 ms** | 読み 139 ms が完全に隠れる |
| A2: 同上、読みを `mx.stream(mx.cpu)` で | 330 ms | 差なし。既定ストリームで足りる |
| B: Python スレッドで次を読む | 335 ms | 動くが A より複雑 |

A を採用。`Krea2StreamedBlock.__call__` は「bind → 計算を投げる → 次のブロックを
読んで実体化 → 計算を待つ → drop」の順になり、最後のブロックは次のステップの
block 0 を読む。実体化した次のブロックは `Krea2BlockStream.ready` に 1 つだけ入り、
使うブロックが `take` で持ち出す(以後は従来どおり lazy ハンドルに戻して drop)。

## 2. 分かったこと

- **見えている I/O は 137 → 1 ms。** 1024² のステップ時間は予測 9.2 s に対し 9.42 s。
- **常駐は +0.46 GB** で 1 ブロック分ちょうど。上限まで 1280² でも 5.8 GB 残る。
- **1280² の計算がブロックあたり +32 ms 遅くなった**(541.6 → 573.4 ms)。
  読みの裏で GPU が遅くなっているのか、持続負荷でクロックが落ちているのか
  (1280² はステップごとに 15.5 → 16.2 s と伸びている)は切り分けていない。
  1024² では +5 ms で誤差の範囲。M8e(`powermetrics`)の宿題に含める。
- 常駐版とビット一致のテスト(`tests/test_krea2_block_streaming.py`)はそのまま通る。
