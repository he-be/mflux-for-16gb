# M7: M6 mac mini 16GB の実機 → **合格**(1280² も clean)

- 測定日: 2026-09-22
- 機材: **Mac mini (Apple M6) 16GB**、macOS 27.0 (26A428)、MLX 0.32.0、GPU 12 コア
- 実装: `dcacf52`(`--block-streaming`)
- 接続: Thunderbolt bridge 経由の ssh(`~/.ssh/config` の `m6-tb` = 169.254.24.129)
- 再現: 下の §2 / §3

M3 Pro 18GB で通した構成(M6)を、**本来の目的だった 16GB 機**にそのまま移して
回す。合わせて **M6 の GPU neural accelerator を MLX が実際に使っているか**を
Metal のキャプチャで確認する。

## 0. 結論

| | |
|---|---|
| 1024² / 4 ステップ | **20.9〜21.2 s/step**、footprint **5.32 GB**、**swapouts 0**、verdict `clean` |
| 1280² / 4 ステップ | **35.21 s/step**、footprint **6.46 GB**、**swapouts 0**、verdict `clean` |
| `iogpu.wired_limit_mb` | **既定の 0 のまま**。特別な設定は何も要らない |
| neural accelerator | **使われている。** DiT も text encoder も `affine_qmm_t_nax_*` に落ちる(§4) |
| 再現性 | 同じ機械で 2 回 → **ピクセル完全一致**(0 / 1048576) |

**18GB 機より 2GB 少ないのに、1280² でも 6.46 GB しか使わずに通る。**
M3 Pro より 1 ステップあたり **1.42 倍速い**。

## 2. 転送(何を送ったか)

リポジトリと**前処理済みのウェイト**を送るだけ。mini 側で bake も量子化もしない
(元の q8 スナップショット 21 GB を送る必要がなくなる)。

```sh
# 1. リポジトリ(.venv は送らない。256 MB)
rsync -a --exclude .venv --exclude __pycache__ ~/dev/mflux/ m6-tb:dev/mflux/

# 2. 低メモリ用スナップショット(合計 17 GB)
#    symlink を実体化するので -L。mini 側では transformer/ text_encoder/ vae/
#    tokenizer/ が本物のディレクトリになる
B=~/Library/Caches/mflux/16gb-bench
Q8=~/.cache/huggingface/hub/models--mflux-community--krea-2-turbo-mflux-q8/snapshots/ad5c0b1784c486bd45c2ced8a9f10aa45293a7c8
R=Library/Caches/mflux/16gb-bench/krea2-lowram
ssh m6-tb "mkdir -p $R"
rsync -aL $Q8/tokenizer/              m6-tb:$R/tokenizer/       #  11 MB
rsync -aL $Q8/vae/                    m6-tb:$R/vae/             # 499 MB
rsync -aL $B/krea2-te-q8/text_encoder/ m6-tb:$R/text_encoder/   # 4.0 GB
rsync -aL $B/krea2-q8-4step-baked/     m6-tb:$R/transformer/    #  13 GB

# 3. 環境(mini には uv も brew も入っていなかった)
ssh m6-tb 'curl -LsSf https://astral.sh/uv/install.sh | sh'
ssh m6-tb 'source ~/.local/bin/env && cd ~/dev/mflux && uv sync --frozen'
```

| | 時間 | 帯域 |
|---|---|---|
| リポジトリ 256 MB | 1.3 s | 197 MB/s |
| vae 499 MB | 1.9 s | 265 MB/s |
| text_encoder 4.0 GB | 14.6 s | 281 MB/s |
| transformer 13 GB | 45.2 s | 295 MB/s |
| `uv sync --frozen` | 31 s | — |

Thunderbolt bridge 越しの ssh で **約 290 MB/s**。17 GB が 1 分ちょっとで渡る。
`m6-tb` の `Ciphers aes128-gcm@openssh.com` が効いている。

## 4. neural accelerator は使われているか → **使われている**

M6 の GPU コアには neural accelerator(行列演算ユニット)が載っている。
MLX 0.32.0 はこれ向けのカーネルを **`nax`** という名前で持っていて
(`backend/metal/kernels/quantized_nax.h`、`steel/gemm/nax.h`、
`bool is_nax_available()`)、対応ハードなら自動で切り替わる。
Python からは可否を問い合わせられないので、**Metal のキャプチャで
実際にディスパッチされたカーネル名を読む**。

`tools/bench/nax_probe.py` が、DiT が実際に出している形
(`x=[1, 4126, 6144]`、`w=6144×16384`、group_size 64、bits 8)の
`mx.quantized_matmul` を 1 回だけ**コールドで**キャプチャする
(パイプライン名はカーネル生成時にしか trace に書かれないので、
ウォームアップ後に撮ると何も写らない。dtype ごとに別プロセスで回す)。

```sh
MTL_CAPTURE_ENABLED=1 uv run python tools/bench/nax_probe.py
```

**M6 mini (applegpu_g18g)**

| 活性の dtype | 時間 | TFLOPS | ディスパッチされたカーネル |
|---|---|---|---|
| float32 | 82.2 ms | 10.11 | **`affine_qmm_t_nax_float_gs_64_b_8_bm64_bn64_bk64_wm2_wn2_alN_true`** |
| bfloat16 | 48.9 ms | **16.97** | **`affine_qmm_t_nax_bfloat16_t_gs_64_b_8_bm64_bn64_bk64_wm2_wn2_alN_true`** |
| float16 | 81.2 ms | 10.22 | 同 `..._nax_float_...` + `vn_copyfloat16float32`(float32 に上げてから) |

**M3 Pro (applegpu_g15s)** の同じ形は 4.69 / 5.10 / 4.67 TFLOPS。
同じ手順でキャプチャしても `nax` の付く名前は 1 つも出てこない
(ただし macOS 15.6 の trace は qmm カーネルの名前そのものを落としていて、
`affine_quantize_*` など一部しか書かれない。**「nax ではない」の直接証拠は
M3 Pro 側では取れていない**。根拠は TFLOPS の差のほう)。

`tools/bench/qmm_spy.py` で**実際の生成 1 ステップ**の
`mx.quantized_matmul` を全部記録すると 22 種類・515 回。DiT の重い 4 種は

```
x=[1, 4126, 6144]  w=6144×6144   gs=64 bits=8 float32  × 84
x=[1, 4126, 6144]  w=6144×16384  gs=64 bits=8 float32  × 56
x=[1, 4126, 6144]  w=6144×1536   gs=64 bits=8 float32  × 56
x=[1, 4126, 16384] w=16384×6144  gs=64 bits=8 float32  × 28
```

で、いずれも上の表の float32 行と同じ形。text encoder 側は bfloat16 なので
bfloat16 行に落ちる。**生成のホットパスはすべて `nax` カーネルを通っている。**

合成ベンチ(`tools/bench/matmul_probe.py`、5120×6144 @ 6144×6144):

| | M3 Pro | **M6 mini** | |
|---|---|---|---|
| bf16 matmul | 5.90 TFLOPS | **12.35** | 2.09× |
| fp16 matmul | 5.91 | **12.55** | 2.12× |
| fp32 matmul | 4.07 | **11.17** | 2.74× |
| q8 quantized matmul | 5.11 | **17.16** | **3.36×** |
| q4 quantized matmul | 5.15 | **18.49** | **3.59×** |
| sdpa 4096×128×24 | 5.20 | **16.41** | 3.16× |

**量子化 matmul が素の matmul より速いのが neural accelerator の指紋。**
M3 Pro では q8(5.11)が bf16(5.90)より**遅い**。M6 では q8(17.16)が
bf16(12.35)より **1.39 倍速い**。

### 残っている伸びしろ: DiT の活性が float32

上の表のとおり bfloat16 の `nax` カーネルは float32 の **1.68 倍**速い。
mflux の Krea2 DiT は RoPE と RMSNorm を float32 で通す設計なので
(`model/krea2_transformer/rope_embedder.py`、`common.py`)、
ブロック内の matmul も float32 で走っている。
**活性を bf16 に落とせば計算 610 ms → 360 ms 程度まで縮む余地がある**
(1 ステップ 21.2 s → 14.2 s 見込み)。ただし出力の数値は変わるので、
やるなら画像を見比べて判断する話(M5b と同じ扱い)。**今回は触っていない。**

## 5. 出力の一致

| 比較 | 違うピクセル | max abs diff |
|---|---|---|
| **M6 mini 1024² を 2 回**(別プロセス) | **0 / 1048576** | **0** |
| M6 mini 1024² vs M3 Pro 1024² | 947581 / 1048576 (90.4%) | 190(平均 4.61) |
| M6 mini 1280² vs M3 Pro 1280² | 1498051 / 1638400 (91.4%) | 221(平均 4.89) |

**同じ機械では完全に決定的。機械が変わると一致しない。**
M3 Pro と M6 は同じ演算に**別のカーネル**を使う(§4)ので、q8 matmul の
累積順序が違い、4 ステップの拡散でその差が増幅する。平均 4.6 / 255 は
目視では分からない差で、構図・被写体・光は同一。描き込みの量も同等。

> **`--block-streaming` はクロスマシンでビット一致を約束しない。**
> M5 / M6 で確認した「常駐版とビット一致」は**同一機材の中での**性質。
> 機材をまたぐ再現性を数字で要求するなら、比較は同じ GPU 上で行うこと。

## 6. 分かったこと

- **16GB 機でも余裕がある。** 1280² の footprint は 6.89 → **6.46 GB** と
  むしろ下がった(1024² は 5.21 → 5.32 GB でほぼ同じ)。上限まで 10 GB 以上余る。
  この 0.4 GB の差が何由来かは**測っていないので断定しない**
  (`max_recommended_working_set_size` が 16.11 → 12.71 GB と小さいので
  MLX のキャッシュの振る舞いが違う可能性はあるが、確認していない)。
- **mini の SSD は MacBook Pro の半分の速さ。** 1 ブロック 461.3 MB を
  138.2 ms(**3.34 GB/s**)。M3 Pro は 71.9 ms(6.24 GB/s)。
  計算 ÷ I/O は 13.59 → 4.16 に落ちたが、**合格基準 2.0 は余裕で超えている**。
  I/O はステップ時間の 19% を占めるようになった。
  **プリフェッチに初めて意味が出る条件**だが、まだやる必要はない。
- **drop が 7.9 ms → 0.4 ms。** ウェイトの解放コストはほぼ消えた。
- **`iogpu.wired_limit_mb` は既定の 0 のままで通る。** M6 の宿題
  (「15360 の設定下でしか測っていない」)は、**この機械については解消**。
  M3 Pro 側での 0 での再測定はまだ残っている。
