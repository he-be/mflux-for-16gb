# M6: mflux 本体への実装 → **合格**(1280² も clean)

- 測定日: 2026-09-22
- 機材: MacBook Pro M3 Pro 18GB、macOS 15.6、MLX 0.32.0
- 実装: `d9b2f80`(`--block-streaming`)
- 再現: 下の §1 のコマンド

`tools/bench/` の 4 プロセス分割版でしか動かなかったものを、mflux 本体の
**フラグ 1 本**にした。M5 / M5b の数字が CLI 経由でもそのまま出るか、
出力が一致するかを見る。

## 0. 何を作ったか

`--block-streaming` の効果は 3 つ。

1. **段階ロード。** text encoder → 破棄 → DiT → 破棄 → VAE。3 つ同時は 22.2 GB で載らない
2. **ブロック単位ストリーミング。** 28 ブロックをディスクに置いたまま bind → forward →
   `mx.eval` → drop
3. **VAE タイル 256 を既定にする**(`--vae-tile-size` を明示すればそちらが勝つ)

新しいクラスは 2 つだけ。

| | |
|---|---|
| `weights/krea2_weight_stream.py` | `Krea2BlockStream` が index を読んで `transformer.blocks` をラッパのリストに差し替える。`Krea2StreamedBlock` が bind / forward / eval / drop |
| `krea2_staged_loader.py` | `Krea2StagedLoader.build(名前)` がコンポーネント 1 個を作って返す。手放すのは呼び出し側 |

`Krea2.generate_image` の変更は **3 か所を `with self._component(...)` で囲んだだけ**。
常駐モードではこの context manager は素通りするので、既存の挙動は変わらない
(fast テスト 1504 件が緑)。

**低メモリ用スナップショットに新しい形式は要らなかった。** bake 済みの per-block
シャードを `transformer/` に置くと、既存の `_select_transformer_variant` が拾い、
`_try_load_mflux_format` が mflux 保存形式として読む。`--model` 1 本で 3 コンポーネント
すべてが揃う。

## 1. 再現

```sh
uv run python tools/swapwatch.py --csv docs/16gb/runs/<ts>-m6-cli.csv -- \
  uv run mflux-generate-krea2 \
    --model ~/Library/Caches/mflux/16gb-bench/krea2-lowram --base-model krea-2 \
    --block-streaming \
    --prompt "a photograph of a weathered brass diving helmet on a workshop bench, \
morning light through a dusty window, shallow depth of field" \
    --seed 42 --steps 4 --scheduler euler --guidance 1.0 \
    --width 1024 --height 1024 --no-metadata --output out.png
```

スナップショットの組み立て方は [README](../README.md#実行のしかた) にある。

## 3. 1280²(LoRA の学習 σ と一致する解像度)→ **clean**

σ の動的シフトは 1280² で μ=1.15 になり、4step LoRA の学習点と一致する
(1024² は μ=0.906 でわずかにずれる)。

| | |
|---|---|
| 1 ステップ | **48.91 s** |
| I/O / ブロック | 72.1 ms(1024² と同じ。ウェイトの量は解像度に依らない) |
| 計算 / ブロック | 1653.3 ms |
| 計算 ÷ I/O | **22.92** |
| mx peak | **4.47 GB**(= TE の段。DiT はこれを超えない) |
| 実 footprint | **6.89 GB** |
| swapouts | **0** |
| verdict | **clean** |
| 合計時間 | 208 s |

出力: `images/20260922-1129-m6-cli-1280.png`。**1024² より明らかに描き込みが多い。**
腐食のピット、ボルト、窓の結露、工具の質感 — LoRA の学習解像度で回した効果が出ている。

アクティベーションは 1024² の 1.94 GB に対して (1280/1024)² = 1.56 倍なので約 3.0 GB。
footprint が 5.21 → 6.89 GB に増えた分(+1.68 GB)とおおむね合う。
**常駐方式なら 13.62 + 3.0 = 16.6 GB で、1024² より深くスワップしていたはず。**

## 4. 56 ページの件(1024² 実行での `SWAPPED` 判定)

1024² の実行は swapwatch が `SWAPPED` と出した。**中身は 56 ページ = 0.9 MB。**

CSV を見ると、t=22.3 s の 1 サンプルだけで起きている。

```
t=20.2  swap_used 307.8  swapouts 2614066  swapins 1374721  child 2236 MB
t=22.3  swap_used 286.8  swapouts 2614122  swapins 1374802  child 3710 MB
        └ 21 MB 減った    └ +56             └ +81
```

**swap used が 21 MB 減り、swapins が 81 ページ増えている。**
これは他のプロセスがページを読み戻している最中の挙動で、56 ページの押し出しは
その裏返し。自プロセスの footprint は 3710 MB で動いていない。
swapwatch の swapout カウンタは**マシン全体**なので、この規模の値は
自分の実行によるものと区別できない。

**1280² の実行が決着をつけた。** より重い要求(footprint 6.89 GB)で 208 秒回して
**swapouts 0**。同じベースライン(2614122 ページ)から 1 ページも増えていない。
1024² の 56 ページは外来。

## 5. 実装で踏んだもの

- **`mx.compile` は切らないと通らない。** `Krea2._predict` は M1/M2 以外では
  `mx.compile(predict)` を返す。ストリーミングされたブロックは forward の中で
  ディスクを読み `mx.eval` を呼ぶので、トレースに乗らない。
  判定は `self.staged_loader is not None` で行う(transformer の中身を覗かない)。
- **TE を手放す前に `mx.eval(embeds)` が必要。** 遅延評価のままだとグラフが
  エンコーダのウェイトを掴んだままで、参照を捨てても 1 バイトも解放されない。
  `_component` を抜けるところではなく、**with ブロックの中で** eval する。
- **`staged_loader` はクラス属性の既定値として持つ。** `Krea2.__new__(Krea2)` で
  組み立てるテスト(`tests/vae/test_decode_honours_tiling_config.py` など)が
  あるので、`__init__` だけで設定すると AttributeError になる。
- **TE の component は `skip_quantization=False` に差し替える。** 定義が True のままだと
  量子化構造を作らずに packed な q8 テンソルを update してしまう
  (M5b で `tools/bench/quantize_te_checkpoint.py` が同じことをしている)。

## 7. 残っていること

  15360 の設定下で測っている。ストリーミングにこの設定は不要なので**既定の 0 に
  戻した状態で通ることを確認する**(それがこの方式の価値なので)。sudo が要る:
  `sudo sysctl -w iogpu.wired_limit_mb=0`

  ピクセル完全一致しているので、再現性は実質示されている。
