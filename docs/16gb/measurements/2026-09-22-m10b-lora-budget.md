# M10b: 実行時 LoRA の +81 ms はどこに行っていたか(2026-09-22 夜)

機材: Mac mini (Apple M6) 16GB。[M10](2026-09-22-m10-runtime-lora.md) が
**アダプタの FLOPs は 1.3% なのに 1 ステップ +30%** という釣り合わない数字を出したので、
1 ブロックを 1 プロセスで分解した。道具は `tools/bench/lora_budget.py`。

## 結論: スカラー倍がフル幅の出力を舐めていた。−1.07 s/step

`LoRALinear.__call__` は `base(x) + scale * (x @ A @ B)` だった。
`scale *` は**基底層と同じ幅**のテンソルを 1 本余計に作って捨てる。
Krea 2 の `mlp.gate` / `mlp.up` は出力が 16384 幅で、1024² では 1 層 135 MB。

**スカラーを rank-r の中間テンソル側に移すだけでいい。**
`base(x) + (scale * (x @ A)) @ B` は同じ値で、掛ける相手が (tokens, 64) の数百 KB になる。
事前計算も dtype 変更も要らないので、mflux の全モデルの全アダプタに効く。

```
src/mflux/models/common/lora/layer/linear_lora_layer.py
src/mflux/models/common/lora/layer/fused_linear_lora_layer.py
```

## 1. 1 ブロックの比較(本番形、4126 トークン = 1024²、rank 64 を 8 層、`down_splits=4`)

| | 時間 | ブロックへの増分 |
|---|---|---|
| アダプタなし | 275.6 ms | — |
| **`LoRALinear` 現行** | 357.1 ms | **+81.4 ms** |
| scale を B に事前畳み込み | 325.5 ms | +49.9 ms |
| **scale を rank-r の中間に**(採用) | **322.5 ms** | **+46.9 ms** |

本番の実測 +81.7 ms([M10](2026-09-22-m10-runtime-lora.md))をプローブが +81.4 ms で
再現している。**`down_splits` を 4 にするまでは base が 316 ms で増分も食い違っていた**
——M8c の「本番形で測る」はここでも効いた。

## 2. アダプタ単体の内訳(ブロックの外、1 層ずつ)

| 層 | 出力幅 | A のみ | A→B | +スカラー | +加算 | 中間スケール |
|---|---|---|---|---|---|---|
| attn.wq | 6144 | 0.7 | 1.2 | 1.9 | 3.0 | 2.3 |
| attn.wk | 1536 | 0.7 | 0.9 | 0.9 | 1.2 | 1.1 |
| attn.wv | 1536 | 0.7 | 0.9 | 1.0 | 1.2 | 1.1 |
| attn.gate | 6144 | 0.7 | 1.2 | 1.9 | 3.0 | 2.3 |
| attn.wo | 6144 | 0.7 | 1.2 | 1.9 | 3.0 | 2.3 |
| **mlp.gate** | **16384** | 0.7 | 1.9 | 3.8 | **6.8** | 4.8 |
| **mlp.up** | **16384** | 0.7 | 1.9 | 3.9 | **6.8** | 4.8 |
| mlp.down | 6144 | 1.7 | 2.1 | 2.9 | 4.0 | 3.3 |
| **合計** | | **6.6** | **11.2** | **18.1** | **28.9** | **21.9** |

行列積そのものは 11.2 ms。**スカラー倍で +6.9、加算で +10.8** と、
要素演算がアダプタの時間の 6 割を占めていた。16384 幅の 2 層だけで 13.6 ms。

単体合計 28.9 ms に対してブロック内では +81.4 ms。差の 52 ms は
M8 / M9b と同じ「鎖が開く」分(生きたテンソルが増え、カーネルが増える)で、
中間スケールにしても 21.9 → +46.9 ms と比率は変わらない。

**dtype は健全**(x / A / B / base / 和 すべて bf16)。M8 の float32 伝播の再発ではない。

## 3. 本番での効果(M6 mini / 1024² / 4 ステップ / swapwatch)

| | 1 ステップ | 計算/ブロック | 実 footprint | verdict |
|---|---|---|---|---|
| LoRA なし | 7.92 s | 282.2 ms | 5.16 GB | clean |
| LoRA(現行) | 10.32 s | 363.9 ms | 6.62 GB | clean |
| **LoRA(中間スケール)** | **9.25 s** | **328.1 ms** | **5.79 GB** | **clean** |

**−1.07 s/step(−10%)、footprint −0.83 GB。** 捨てていたフル幅の中間テンソルが
そのままメモリでもあったので、速度と常駐が同時に下がる。
LoRA なしに対する増分は **+30% → +17%**。
ログ: [`runs/m6mini/20260922-2130-m10b-lora-narrow.csv`](../runs/m6mini/20260922-2130-m10b-lora-narrow.csv)。

## 4. 残りの +17% を消す手: 焼き込み

実行時の側道である限り +46.9 ms/ブロックは残る。**ゼロにする方法は 1 つだけで、
チェックポイントに焼き込むこと。** `tools/bench/bake_lora_checkpoint.py` は
**既に焼き込み済みの `krea2-lowram` の上にもう 1 枚重ねられる**(実測)。

```
uv run python tools/bench/bake_lora_checkpoint.py \
  --model ~/Library/Caches/mflux/16gb-bench/krea2-lowram \
  --out   ~/Library/Caches/mflux/16gb-bench/studio-presets/<name> \
  --lora-path <style.safetensors> --lora-scale 0.8
```

| | |
|---|---|
| 時間 | **15.4 s**(wrap 2.0 + blocks 11.7 + globals 0.6) |
| mx peak | 1.89 GB |
| 出力 | **13 GB**(1 組み合わせあたり) |
| 焼いた後の速度 | **7.92 s/step**(LoRA なしと同じ。実行時コストゼロ) |

**採算**: 1 枚あたり 4 ステップ × 1.33 s = 5.3 秒得をするので、**3 枚で元が取れる**。
mini の空きは 144 GB なので 10 組ほど置ける。**scale を変えると焼き直し**になる
(量子化してから足すので scale について線形にならない)。

→ 試行錯誤は実行時(9.25 s/step)、**決まったら 1 回焼く(15 秒)**、という使い分けが答え。
studio に組み込むかは別途。

## 5. 効かなかった / やらなかった手

- **scale を B に事前畳み込み**: +49.9 ms。中間スケール(+46.9)より遅く、
  B を 1 回 bf16 で丸める副作用もあるので不採用。
- **`mx.compile` で silu・乗算・加算を融合**: [M9b](2026-09-22-m9b-block-budget.md) が
  ブロック全体でも部分でも遅くなると結論済み。再試行していない。
- **A を入力ごとに連結**(wq/wk/wv/gate は同じ x、mlp.gate/up は同じ o):
  A 側の合計が 6.6 ms しかないので、上限が小さい。中間スケールを入れた後に
  まだ足りなければ。
