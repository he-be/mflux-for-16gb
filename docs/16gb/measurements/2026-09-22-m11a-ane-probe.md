## 1. この文書の訂正(初版 2026-09-22 の誤り)

初版は結論の理由を「**行列積が帯域律速で ANE と GPU がメモリ帯域を食い合うから**」と書いた。**これは誤りで、撤回する。**
検算すると、

| | FLOP | 動かすバイト | 演算強度 | 実効帯域 |
|---|---|---|---|---|
| GPU `gate` 6144→16384 @ 16.90 TFLOPS | 0.83 TFLOP | 293 MB | **2836 FLOP/byte** | **6.0 GB/s** |
| ANE `mlp57` @ 15.38 TOPS | 1.42 TFLOP | 約 505 MB | 2810 FLOP/byte | **5.5 GB/s** |

M6 mini のバスは少なくとも 120 GB/s。**合わせて 1 割も使っていない**ので、DRAM 帯域の食い合いでは説明できない。
M9 §2 で「帯域律速」と書いたのは **K=16384 の崖の中だけ**の話で、それを全体に広げたのが誤り。

初版の誤りは 3 つ:

1. **測っていない機構(帯域)を結論の理由として書いた。**
2. **合成の同居人(`ceiling_probe` 式の行列積連打)で本番の可否を決めた。** — これは計画 §4-3 の指定でもあり、
   計画の時点で間違っていた。本番で測り直したのが §2。
3. **干渉の係数を MLP の相にだけ掛けた**(attention と要素演算を素通しにした)ので、見積りが
   「ほぼ同じ 7.8 s/step」になった。正しくはブロック全体に掛かり、**15.2 s/step**(§11)。

なお 2 の「合成は本番より厳しいはず」という予想も外れていた。**合成 0.40 倍に対し本番 0.46 倍で、
GPU の落ち方はほぼ一致していた**(§3)。合成テストは正しく、それを本番の数字に翻訳した計算が誤っていた。

また合格基準 5(数値)は、計画 §4-7 自身が「**画像で判定する**」と決めているのに ULP の表で落とした。
判定は §11 のとおり基準 1 / 2 で決まるので結論は変わらないが、5 は「未判定」が正しい。

## 3. 増えた時間はどこに入ったか → **全部 compute、prefetch は不動**

`stream_ab.py --config main:1`(本番のストリーミングループを compute / prefetch / bind / drop に分解)。

| | compute(ms/block) | **prefetch** | bind | drop | step(28 ブロック) |
|---|---|---|---|---|---|
| 単独 | 323.3 / 338.7 | **140.4** | 0.0 | 0.2 | 9.06 / 9.49 s |
| **+ANE `mlp57`** | **724.9 / 722.1** | **140.5 / 140.4** | 0.0 | 0.2 | **20.30 / 20.22 s** |

## 5. ANE が受ける int8 は行スケールだけ

`ios18.linear->GPU` が compute plan に出る = Core ML が **group-64 の blockwise int8 を ANE に載せない**。
選べるのは 2 つだけ:

- **行スケール int8** — ANE に載る。速い(15.4)。GPU の q8 とは丸めが変わる(§9)。
- **fp16 重み** — ANE に載る。数値は良い。**6.5 TOPS しか出ない**。

GPU 側の q8 は affine の group-64(scale + bias)なので、ANE に渡すには必ず再量子化を通る。
**「同じ q8 のまま ANE に載せる」経路は存在しない。**

- **ANE 側の電力は測れない。** M6 に ANE 専用レールの報告がなく、`ane_power` サンプラは 1 行も出さず、
  ANE 全開でも `Combined Power (CPU + GPU + ANE)` は 4 mW のまま。

**なぜこうなるのかは、この測定からは決まらない。** クロック・電力・速度の 3 つが同時に下がったという事実だけで、
どれが原因でどれが結果かを区別する測定はしていない。**この文書では機構を名指ししない。**

## 14. 付随して分かったこと

**ベースラインの 1 生成が 56 GB ページインしている。** 461.3 MB/block × 28 × 4 step = 51.7 GB とほぼ一致する。
つまり**ブロック重みは毎ステップ毎ブロック、ページキャッシュではなくディスクから読み直している**
(`krea2-q8-checkpoint-layout` の 6.24 GB/s の経路。prefetch 140.4 ms/block はこれ)。
M11a とは独立の観察で、別途 M9f / M12 の材料。

**Irodori-TTS の構成(引用)。** `note-mac.md:106`:「DiT を ANE に移すと GPU が丸ごと余る。だから同じ生成の中で
GPU 側に**別の分岐**を並走させられる。実際、CFG の 3 分岐のうち 1 本は GPU に投げて同時に回している」。
`note-mac.md:74`: M3 Pro の GPU は fp16 で 5.6 TFLOPS、「DiT の 1 ステップは 1.5GB の重みを毎回読み直す」。
得られた高速化は 1.25〜1.35 倍(`note-mac.md:94`)。
こちらの案は同じ MLP を列で割って同じブロックの中で GPU と ANE を回すもので、本番で測ると 1 ステップが 2.3 倍。
**両者の差がどこから来るかは、この測定では扱っていない。**
