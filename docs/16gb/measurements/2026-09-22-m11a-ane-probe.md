# M11a: ANE を 2 台目の演算器にできるか → **できない。GPU が 60% 落ちる**

- 測定日: 2026-09-22
- 機材: Mac mini (Apple M6) 16GB、macOS 27.0、GPU 12 コア、**ANE は compute plan が 32 コアと報告**(16 コア × 2 基が 1 デバイス)
- 再現: `tools/bench/ane_probe.py`(coremltools 9.0、MIL 直書き、torch 不要)
  - `UV_PROJECT_ENVIRONMENT=.venv313 uv run --python 3.13 --with coremltools python tools/bench/ane_probe.py --json ...`
  - **Python 3.14 では動かない**(§1)
- 生データ: [`20260922-2306-m11a-ane-probe.json`](../runs/m6mini/20260922-2306-m11a-ane-probe.json)、
  [`20260922-2343-m11a-actstats.json`](../runs/m6mini/20260922-2343-m11a-actstats.json)
- 計画: [ANE を 2 台目の演算器に](../../.cursor/plans/2026-09-22-krea2-ane-hybrid.md) §5 M11a
- 重みは実 block 0(`Krea2BlockStream.read(0)`)を `mx.dequantize` してから再量子化。ウォームアップ 3、10 回平均
- GPU 側の比較値は M9 と同じ `ceiling_probe` 系のループ(q8 6144→16384、**単独 16.90 TFLOPS**)

## 0. 結論

| | |
|---|---|
| ANE 単独、候補の形(MLP の 57% 列、int8 行スケール) | **15.4 TOPS**(92.4 ms)。GPU の q8(16.9)とほぼ同じ |
| デュアル ANE は 2 倍になるか | **ならない。2 プロセスで +34%**(13.10 → 17.50 TOPS)。2 スレッドは +0% |
| **GPU と同時に回したとき** | **ANE 15.4 → 9.5 TOPS、GPU 16.90 → 6.78 TFLOPS(−60%)** |
| 受け渡し(`shared_memory`、51 MB 入 / 51 MB 出) | 往復 103.4 ms のうち **オーバーヘッド 3.5 ms**(合格) |
| ANE が受ける int8 は**行スケールだけ** | group-64 は Core ML が **GPU に落とす**(`linear->GPU`)。ANE に載らない |
| その行スケール int8 の数値 | GPU 比 mean abs 0.50、**79% の要素が bf16 1 ULP 超**。norm の bf16 化(M9b §5、33%)の桁ではない |
| fp16 活性のレンジ | **問題なし**。実走の最悪は block 7 の `silu(g)*u` = 1944 = fp16 上限の **2.97%** |
| §3 のモデルに併走の実測を戻すと | 1 ブロック 281.5 → **約 275 ms**(1 ステップ 7.9 → 7.8 s)、その代わり **+5.7 GB** |

**M11a は合格基準 5 つのうち 3 つを外した(§9)。計画どおり M11b には進まない。**

理由は 1 行で言える: **この行列積はどれも演算律速ではなく帯域律速で、ANE と GPU は同じ
メモリ帯域を食い合う。** 演算器を足しても帯域は足されないので、ANE が取った分だけ GPU が遅くなる。
M9 で「シリコン側に隠れた性能はない」と書いたのと同じ壁に、別の演算器から当たった。

## 1. 踏んだもの: Python 3.14 に coremltools のネイティブが載らない

`uv run --with coremltools` は Python 3.14 環境に coremltools 9.0 を入れるが、**import は通るのに
ネイティブ拡張が 1 つも載らない**:

```
Failed to load _MLModelProxy: No module named 'coremltools.libcoremlpython'
Fail to import BlobWriter from libmilstoragepython
  gate-m4126-row    FAILED: BlobWriter not loaded
```

cp314 の wheel がなく、純 Python 部分だけが入るため。**`import coremltools` の成功は環境確認にならない**
(`from coremltools.libcoremlpython import _MLModelProxy` まで見る)。3.13 と 3.12 では載る。
mini では 3.14 の `.venv`(studio が使っている)を壊さないよう、並行の venv を切って回した:

```sh
UV_PROJECT_ENVIRONMENT=.venv313 uv run --python 3.13 --with coremltools python tools/bench/ane_probe.py ...
```

**unified log に ANE のコンパイル失敗は 1 件もなかった**(`Model load failed` / `Compilation failed` /
`Register spiller failure` すべて 0)。以下の遅さは静かな CPU 落ちではなく、本当に ANE で出ている数字。

## 2. 単体の TOPS(ANE 1 基のみ、GPU は空き)

| 形 | M | int8 行 | int8 g64 | fp16 重み | 載った先 |
|---|---|---|---|---|---|
| `wq` 6144→6144 | 4126 | **10.76** | 8.93 | 6.55 | 行/fp16 は NE、g64 は GPU |
| `gate` 6144→16384 | 4126 | **13.07** | 9.89 | 7.37 | 同上 |
| `gate` 6144→16384 | 6430 | **13.12** | 10.14 | 7.18 | 同上 |
| **`down` 16384→6144** | 4126 | **3.65** | 6.76 | 3.68 | 同上 |
| **`down` 16384→6144** | 6430 | **1.32** | 7.12 | 1.32 | 同上 |
| `mlp` 全列(gate+up+down 融合) | 4126 | 9.41 | 5.61 | 6.70 | linear×3 が NE、silu / mul も NE |
| **`mlp57` 57% 列(候補)** | 4126 | **15.38** | 5.02 | 6.55 | 同上 |
| **`mlp57` 57% 列(候補)** | 6430 | **15.52** | 5.61 | 6.49 | 同上 |

- **`down`(K=16384)は ANE でも崩れる。** GPU の MLX が 9.1 TFLOPS で MPS が 17.9 だった(M9 §1)のと違い、
  ANE は 3.65、M=6430 では **1.32**。K が大きい形は ANE の弱点でもある。
  `mlp57` が速いのは down の K が 9344 に縮むから(M8c の K 分割と同じ理屈)。
- **fp16 重みは 6.4〜7.4 TOPS で頭打ち。** 重みのバイト数に比例していて、ここでも帯域律速。
- コンパイル時間は融合 MLP で長い(初回 63〜251 s)。**2 回目のロードは 0.02 s**(OS キャッシュ、TTS と同じ)。
  28 ブロック分を焼くのは 1 回なら許容できる。

## 3. ANE が受ける int8 は行スケールだけ

`ios18.linear->GPU` が compute plan に出る = Core ML が **group-64 の blockwise int8 を ANE に載せない**。
つまり選べるのは 2 つだけ:

- **行スケール int8** — ANE に載る。速い(15.4)。**数値が悪い**(§7)。
- **fp16 重み** — ANE に載る。数値は良い。**6.5 TOPS しか出ない**(GPU の 16.9 に対して論外)。

GPU 側の q8 は affine の group-64(scale + bias)なので、ANE に渡すには必ずこの再量子化を通る。
**「同じ q8 のまま ANE に載せる」経路は存在しない。**

## 4. デュアル ANE は 2 倍にならない(+34%)

| 形 | 1 プロセス | 2 プロセス | 1 プロセス 2 スレッド |
|---|---|---|---|
| `gate` row | 13.10 | **17.50**(×1.34) | 13.38(×1.02) |
| `mlp57` row | 14.78 | **16.68**(×1.13) | 14.80(×1.00) |
| `mlp` row | 9.32 | 9.66(×1.04) | 9.32(×1.00) |

- 1 モデルの compute plan が既に **`ane_cores: 32`** と言う。2 基は OS に 1 デバイスとして束ねられていて、
  プロセスを分けても取り分が増えるだけ(+13〜34%)。**「2 基あるから 2 倍」は成立しない。**
- 2 スレッドは完全に無意味(TTS の「predict が GIL を握る」と整合)。
- 形が大きいほど伸びない(`mlp` 全列は +4%)。既に帯域を使い切っている。

## 5. GPU と同時に回すと両方落ちる ← ここで閉じる

GPU 側は q8 6144→16384 のループ(単独 **16.90 TFLOPS**)。重なりは 16〜26 s。

| ANE が回した形 | ANE 単独 → 併走 | GPU 単独 → 併走 |
|---|---|---|
| `gate` row | 12.46 → **9.46** | 16.90 → **13.35(−21%)** |
| `gate` fp16 | 7.05 → 5.22 | 16.90 → 12.15(−28%) |
| **`mlp57` row(候補)** | 13.86 → **9.47** | 16.90 → **6.78(−60%)** |
| `mlp57` fp16 | 6.46 → 3.93 | 16.90 → 5.91(−65%) |
| `mlp` row | 8.94 → 5.52 | 16.90 → 5.34(−68%) |
| `gate` g64(実体は GPU) | 9.97 → 4.59 | 16.90 → 5.48(−68%) |

- **GPU の低下は合格基準の 5% に対し 21〜73%。** 桁で外している。
- ANE 側も 25〜39% 落ちる。**どちらも相手に譲っていて、合計は増えていない。**
- `gate` 単発(−21%)より融合 MLP(−60%)のほうが重い。ANE が連続で回るほど帯域を占有する。
- `g64` の行は ANE ですらない(GPU 上の Core ML)ので、単に GPU の取り合い。参考値。

## 6. 受け渡しは安い(唯一きれいに合格した項目)

| 形 | 往復 | うち predict | **オーバーヘッド** | 入 / 出 |
|---|---|---|---|---|
| **`mlp57` row** | 103.4 ms | 99.9 | **3.5 ms** | 51 / 51 MB |
| `mlp` row | 280.4 ms | 276.8 | 3.6 ms | 51 / 51 MB |
| `gate` row | 76.9 ms | 70.6 | 6.2 ms | 51 / **135 MB** |

`shared_memory` 越しに 51 MB 入 + 51 MB 出して **3.5 ms**。基準の 5 ms 以内。
`gate` 単発が 6.2 ms なのは出力が 135 MB あるから。**MLP を融合して渡せば受け渡しは問題にならない。**

## 7. 数値: 行スケール int8 が壊す(fp16 ではなく)

block 0 の MLP、正規乱数の入力、fp32 を真値として:

| | max abs | mean abs | mean rel | **bf16 1 ULP 超** | 動いた要素 |
|---|---|---|---|---|---|
| GPU bf16 q8(down K4)vs 真値 | 13.91 | 0.106 | 2.82% | 34.8% | 100% |
| **ANE 行 int8 fp16 vs 真値** | 10.43 | **0.488** | 17.5% | **79.6%** | 100% |
| ANE g64 int8 fp16 vs 真値 | 5.82 | 0.240 | 8.35% | 62.6% | 100% |
| **ANE fp16 重み vs 真値** | **1.24** | **0.034** | 1.08% | **12.8%** | 100% |
| ANE 行 int8 vs **GPU**(本番の経路) | 16.00 | 0.500 | — | **79.1%** | 98.7% |
| ANE fp16 重み vs **GPU** | 14.00 | 0.112 | — | 34.6% | 94.8% |

- **fp16 の活性は悪くない。** fp16 重み版は真値に対して GPU の q8 より**近い**(mean abs 0.034 対 0.106)。
  壊しているのは活性の精度ではなく、**行スケールへの再量子化**。
- 採用候補(行 int8)は GPU 比で **79% の要素が bf16 1 ULP を超える**。M9b §5 で採った norm の
  bf16 化は「33% が動いて全部 1 ULP 級」だった。**同程度ではない。**
- `mean rel` / `max rel` は真値がゼロ付近の要素で発散するので判定には使わない(表に残すが見ない)。

## 8. fp16 活性のレンジは問題なかった

実走(1024²、4 ステップ、seed 42、`--block-streaming`)で 28 ブロック × 4 ステップの max abs:

| | 値 | fp16 上限(65504)に対して |
|---|---|---|
| 最悪の `silu(gate)*up` | **1944.0**(block 7) | **2.97%** |
| 最悪の MLP 入力 | 59.50(block 7) | 0.09% |
| block 17 以降 | `silu(g)*u` は 139〜864 | 1.3% 以下 |

- **余裕は 33 倍。** fp16 の活性でオーバーフローする心配はない。§4-6 の未知数はこれで閉じた。
- block 0〜16 と 17〜27 で 1 桁違う(前半の `silu(g)*u` が 540〜1944、後半が 139〜864)。
  M8a の bf16 活性の観察と同じ分かれ方。

## 10. 併走の実測を §3 のモデルに戻す

計画 §3 は「ANE の実効 R TOPS」を**単独**の数字で置いていた。併走の実測(§5)を入れ直す。
1 ブロック: attention 92 ms + MLP 149 ms + 要素演算 29 ms = 281.5 ms、MLP は 2.49 TFLOP。

| | ANE 実効 | GPU の係数 | 釣り合う a | MLP の相 | 1 ブロック | 1 ステップ |
|---|---|---|---|---|---|---|
| いま(GPU のみ) | — | 1.00 | 0 | 149 ms | 281.5 ms | **7.9 s** |
| 計画の机上(22 TOPS、GPU 無傷) | 22 | 1.00 | 0.57 | 64 ms | 190 ms | 約 5.5 s |
| **実測(行 int8、併走)** | **9.47** | **0.40** | 0.586 | **154 ms** | **約 275 ms**(+受け渡し 3.5) | **約 7.8 s** |
| 実測(fp16 重み、併走) | 3.93 | 0.35 | 0.402 | **255 ms** | 約 376 ms | 約 10.5 s |

- 机上で 1.5〜1.7 倍あったはずの伸びは、**GPU が 0.40 倍に落ちる**ことで丸ごと消える。
  釣り合い点の MLP は 154 ms で、いまの 149 ms より**遅い**。
- 数値を守る fp16 重み版は **1.3 倍遅くなる**。
- そのうえで常駐が **+5.7 GB**(6.2 → 約 12 GB)。16 GB 機では M7 の claimable を割る。

## 11. ここから言えること

- **M6 でも ANE 併用は割に合わない。** 演算器は 2 つになるが帯域は 1 つで、この DiT の行列積は
  どれも帯域律速(M9 §2 の「ビット数に比例して速くなる」と同じ観察)。
  Irodori-TTS で 1.35 倍出たのは **M3 Pro の GPU が 5.6 TFLOPS と弱く、帯域にまだ余裕があった**から。
  M6 mini は GPU 単独で既に帯域を使い切っている。
- Draw Things の 22 TOPS(M4)は**行スケール int8 で、GPU を止めて測った値**なら再現している
  (単独 15.4 は形が違う分の差)。M5 で hybrid を既定にしているのは、こちらとは
  帯域と GPU 性能の比が違うからだと考えるのが自然。
- **残る使い道があるとすれば「GPU を遊ばせている時間に ANE を回す」だが、この設計にその時間はない。**
  ブロックは attention → MLP が直列で、prefetch は既に GPU 側の隙間を埋めている(M8b / M9c)。
- 次に行くなら ANE ではなく、M9 が名指しした **`mlp.down` の MLX カーネル**(9.1 対 MPS 17.9)。
  こちらは同じ帯域のまま 1.3 s/step の取り分がある。
