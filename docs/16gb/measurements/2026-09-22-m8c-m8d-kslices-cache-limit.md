## 1. M8c: 単体では速く、本番では遅い

`Krea2SwiGLU.down`(K=16384)を `mx.quantized_matmul` 4 本の和にする実装で:

| 条件 | 1 分割 | 4 分割 |
|---|---|---|
| 単体、cache あり | 318 ms | 291 ms |
| 単体、毎回 `clear_cache` | 329 ms | 307 ms |
| **本番**(交互測定 1→4→1→4、冷却 90 s、`clear_cache` あり) | 335.3 / 335.2 ms | **372.6 ms** |
| 本番(同上、cache limit あり) | 323.0 / 325.3 ms | **365.7 / 366.0 ms** |
| ストリーミング機構を小さく再現、プリフェッチ**あり** | 321 ms | **355 ms** |
| 同、プリフェッチ**なし** | 323 ms | **290 ms** |
| 同、読み込み時に連続な 4 片へ切っておく、プリフェッチあり | | 354 ms |
| 同、プリフェッチなし | | 284 ms |

- 温度ではない。各実行の前後に固定形の matmul を 5 回回して記録した TFLOPS は
  全部 17.0 で動かない(§3)。
- ページフォルトでもない。`clear_cache` を無くしても(M8d)差は +42 ms のまま。
- スライスのコピーでもない。読み込み時に連続な片に切っておいても 354 ms。
- **裏で走る次ブロックの読み込み(`mx.eval` による 461 MB のファイル読み)と、
  K=4096 の matmul 4 本 + 加算 3 本が干渉する。** 1 本の K=16384 は干渉しない。
  なぜ K=4096 の形だけが影響を受けるかは分かっていない(メモリ帯域の取り合いを
  疑うが、読み込みは 3.4 GB/s しか使わない)。

本番は常にプリフェッチするので**採用できない**。コードは元に戻した。
K=16384 で nax カーネルが半速になる件そのものは残っている(`qmm_shapes.py` で再現。
MLX 側に報告する価値はある)。

## 2. M8d: `clear_cache` をやめて cache limit にする

全ブロックがまったく同じテンソル形なので、捨てたブロックのバッファは MLX のキャッシュに
残せば次のプリフェッチがそのまま使える。`Krea2BlockStream.attach` で
`mx.set_cache_limit(2 GB)` を設定し、ブロックごとの `mx.clear_cache()` を消した。

- ブロック −12 ms、drop 0.9 → 0.2 ms。
- **footprint はむしろ下がる。** 1280² で 6.92 → **6.07 GB**、M3 Pro の 1024² で
  5.49 → **4.66 GB**(M8f)。上限のないキャッシュより 2 GB の上限のほうが小さく収まる
  (これまでは `clear_cache` の合間にキャッシュが膨らんでいた)。1024² の mini は
  5.72 GB で変わらず。
- 出力は M8b と完全一致(カーネルは変わらない)。

## 3. M8e: 持続負荷でクロックは落ちるか(代替計測)

`powermetrics` は sudo が要るので使えない。代わりに、各本番実行の**直前と直後**に
4126×6144 @ 6144→16384 の q8 matmul を 5 回回して TFLOPS を記録した(`_ab.py`、
記録は残していない。数字は §1 の交互測定のもの):

| 実行 | 前 | 後 |
|---|---|---|
| 1024² × 4 ステップ(48〜53 s)× 8 本 | 17.0〜17.1 | 16.9〜17.0 |

- **1024² の 4 ステップ(約 50 s)ではクロックは落ちない。** ステップ時間も
  9.20 / 9.11 / 9.19 / 9.32 s で平坦。
- 1280²(64 s)はステップごとに 15.50 → 15.95 s と **+3%** ずつ伸びる。
- M8 §5 の「2 分の連続負荷で 17 → 14.5」は、数分連続で回したときにだけ出る。
  1 枚生成する分には効かない。連続生成の性能を保証したいなら `sudo powermetrics
  --samplers gpu_power -i 1000` を並走させて GPU 周波数を見る(**未測定**)。
