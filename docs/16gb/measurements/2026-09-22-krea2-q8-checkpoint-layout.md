# M0: Krea 2 Turbo q8 チェックポイントの物理配置と読み出し

- 測定日: 2026-09-22
- 機材: MacBook Pro M3 Pro 18GB、内蔵 SSD
- 対象: `mflux-community/krea-2-turbo-mflux-q8`(`quantization_level: 8`, mflux 0.18.0 で保存)
- 出典: `model.safetensors.index.json` と各シャードの safetensors ヘッダ(推測なし)

## 1. サイズ(ヘッダの `data_offsets` から)

| | サイズ |
|---|---|
| transformer 全体 | **13.623 GB** |
| うち blocks 0〜27 | 12.918 GB |
| うち globals (`first`, `tmlp`, `tproj`, `txtmlp`, `txtfusion`, `last`) | 0.705 GB |
| **1 ブロックあたり** | **461.3 MB**(28 ブロックすべて同一) |
| dtype 内訳 | U32(パック済み量子化重み) 12.82 GB / BF16 0.80 GB |

text encoder 8.045 GB、VAE 0.507 GB を足すと 22.2 GB。

## 2. シャードへの配置

- 28 ブロック × 29 テンソル。シャード単位ではブロック番号順(0〜4, 4〜9, 9〜13,
  13〜18, 18〜22, 22〜27, 27+globals)。

**ただしシャードの内部では、あるブロックのテンソルは連続していない。**
シャード 3 (2.09 GB) を バイトオフセット順に並べると、block 13〜18 のテンソルが
互いに入り組んでいる。block 15 の 29 テンソル(461.3 MB)は、
シャード内の **1.37 GB の範囲に散らばっている**。

つまり index (テンソル名 → シャード名) だけを見た「ブロック順に連続配置」という
読みは**誤り**だった。判定はバイトレベルで測り直す必要がある。

## 3. 読み出し帯域(実シャード、`F_NOCACHE`)

| 読み方 | 量 | 時間 | 帯域 |
|---|---|---|---|
| transformer 全体(7 シャードを順に) | 13.62 GB | 3.05 s | **4.47 GB/s** |
| block 15 の 29 テンソルだけを拾い読み | 461.3 MB | 74 ms | **6.24 GB/s** |
| block 15 が散らばる 1.37 GB を素通しで読む | 1365.6 MB | 220 ms | 6.20 GB/s |

散らばっていても帯域は落ちない。個々のテンソルが十分大きい(100MB、37MB、9MB、
3MB といった単位)ため、NVMe にとっては実質シーケンシャルと同じ扱いになる。

## 4. 判定

**合格。ブロック順に並べ直す工程(M0b)は不要。**
理由は「配置が連続だから」ではなく(§2 のとおり連続ではない)、
**散らばった読み方でも 6.24 GB/s 出るから**。

- 1 ブロックの読み出し: **461.3 MB / 74 ms**
- 1 ステップ(28 ブロック): 12.92 GB / **約 2.1 秒**

この 74 ms が、ブロック単位ストリーミングの I/O 側のコスト。計算側(1 ブロックの
forward 時間)は未測定で、その比が 2.0 を超えるかどうかが M5 の合格基準になる。

## 5. 付記: 誤った中間結論について

この文書の初版は、index のシャード割り当てだけを見て「ブロック順に連続配置、
並べ直し不要」と結論していた。結論(並べ直し不要)は変わらなかったが、
根拠は間違っていた。バイトオフセットを見て初めて分かったことなので、
以後 index レベルの観察で配置を語らない。
